# M4 培训档案：功能项差距分析与推进顺序梳理

> 本文件是**分析与排序记录**，不是实施授权。实施授权只来自已确认 OpenSpec Change。
> 排查日期：2026-09-24。范围：中山 50 功能项 44（个人档案 / 企业档案 / 一期一档），
> 及上游功能项 33、34、36。原始范围见 `docs/product/功能项.csv` 与
> `docs/product/安全教育培训需求规格说明书.md`。

## 0. 结论摘要

1. **功能项 44 三个子项整体"部分符合"**，偏差不是零散漏项，而是源数据 → 归档 → 展示三层同时漏。
2. **影像记录不应绑死线下培训**。功能项 36 把影像定义为「培训资料」的一种，与"培训附件"并列，
   边界是"培训过程中"，未限定线下。应挂"培训计划 + 可选阶段"。
3. **签到是"线下培训真实到场"的证据**，服务于监管检查与法定学时留档。它被删是技术前置被清理，
   不是业务需求消失，所以功能项两处仍要求它——这是当前必须正面回答的矛盾。
4. **档案文件格式按最小闭环取 PDF 单文件正本**，不打包影像原件；PDFBox 已在依赖中，无需新增依赖。
5. **企业档案跨租户口径不改**，功能项"所有企业"按"当前租户内所有企业"理解。

## 1. 影像记录应该挂在哪一层

### 1.1 功能项原文依据

| 出处 | 原文 |
|---|---|
| 功能项 36（FR-ENT-TRN-004 培训资料） | 支持上传**培训过程中**产生的影像、培训附件、奖惩评价、综合评价等资料。 |
| 功能项 34（FR-ENT-TRN-003 培训计划实施） | 可维护线上培训、线下培训、培训人员和**附件资料**，并按培训计划添加阶段内容和培训详情。 |
| 功能项 33 | 线下培训：添加培训阶段线下培训，支持线下签到、线下培训考核成绩导入系统，公示培训地点。 |
| 功能项 44 一期一档 | 培训档案内容包括培训计划、企业列表、参训人员、签到情况、学员成绩、综合评价、奖惩、**影像记录**、附件、数据统计等信息。 |

**判断：原文把"影像"定义为「培训资料」的一种，与"培训附件"并列，边界是"培训过程中"，并未限定线下培训阶段。**
功能项 34 也把"附件资料"与"线上培训、线下培训"并列为同级维度，而不是线下培训的子项。

### 1.2 实现层现状：路由已经铺好，只是没接线

- `TrainingAttachment`：`trainingPlanId`（必填）+ `planStageId`（**可空**）→ 档案资料天然就是
  "挂培训计划、可选挂阶段"的结构，与功能项口径一致。
- `attachmentType` 是自由字符串（`TrainingAttachmentCreateRequest` 里为 `@NotBlank String`），
  **没有枚举约束**；后端 CRUD 完整（`/api/training/attachments`，权限 `training:attachment:add/edit/delete/list`）。
- 前端**只有查询、没有上传**：`getTrainingAttachmentPage` 是全前端唯一调用点
  （`frontend/pc-web/src/api/training-process.ts:84`）；POST/PUT/DELETE 前端零引用。
- 前端**附件页签被整体注释**：`PlanProcessResultsPanel.vue` 的附件 `ElTabPane` 与
  `attachmentTypeText` 一起被注释（约 212 行与 315–322 行）。注释里已写好类型映射：
  `GENERAL 一般资料 / IMAGE 图片 / VIDEO 视频 / REWARD_PENALTY 奖惩佐证 / EVALUATION 评价佐证`。
- 归档侧：`sts_archive_asset.asset_type` 已预留 **`IMAGE` / `VIDEO`**，并有
  `source_attachment_id` 回指来源附件；但 `ArchiveAsset` / `ArchiveAssetMapper` **全仓零引用**，从不写入。

### 1.3 结论

**挂"培训计划 + 可选阶段"，不要绑死线下培训。** 理由：

1. **原文口径**：功能项 36 的边界是"培训过程中"，线上培训的开班、直播截图同样计入。
2. **不堵路**：`planStageId` 可空的结构本身已支持两种挂法；绑死线下等于用实现口径收窄功能项。
3. **载体已被削弱过一次**：线下培训阶段的签到能力已被删除（见第 2 节），把影像再压到这个载体上，
   会让两个能力互相牵连。

线下培训阶段会是**最常见的关联对象**，但应作为可选关联而非强制约束。

## 2. 签到的业务含义与现状矛盾

### 2.1 甲方为什么要求签到

签到是**线下培训"人真的到场了"的凭证**。在安全教育培训（尤其安全生产培训）场景：

- 线下培训常伴随**法定学时要求**，需要能证明规定学时真实完成；
- 监管检查、事故倒查时，需要证明**培训真实发生且人员真实到场**；
- 签到表就是这份真实性证据链的**原始记录**。

所以档案要求"签到情况"，本质是要求档案能证明**这次培训不只是系统里走了个流程**。
这也是为什么"签到情况"和"影像记录"会出现在同一句档案内容清单里——两者在业务上是**同一诉求
（培训真实性证据）的两种载体**。

### 2.2 功能项与规格的原文分布

| 出处 | 原文要点 | 当前状态 |
|---|---|---|
| 功能项 33 | 线下培训阶段支持**线下签到**、考核成绩导入、公示培训地点 | 签到能力已删除 |
| 功能项 44 企业档案（FR-ENT-OPS-009） | 详情可查看……**签到情况**、学员成绩…… | 无数据源 |
| 功能项 44 一期一档（FR-ENT-OPS-010） | 档案内容包括……**签到情况**、学员成绩…… | 无数据源 |
| 规格 FR-ENT-TRN-002 | 线下培训可配置签到、考核成绩导入和培训地点 | 签到配置已删除 |
| 规格 FR-ENT-TRN-005 | 支持记录**线下签到**和导入线下培训考核成绩 | 签到记录已删除 |
| 规格 FR-LRN-009 | 学员可参加线下培训签到并参与培训评价；**签到方式和有效条件待确认** | 学员端无签到 |

注意 **FR-LRN-009 自己就写明"签到方式和有效条件待确认"**——也就是说签到口径在需求阶段从未定稿。

### 2.3 签到是怎么被删掉的

- `2026-09-09-zero-hours-for-absent-offline-attendance`：曾存在"缺席线下培训 → 0 学时"的规则。
- `2026-09-10-remove-offline-sign-in-from-plan-apis`（TRAIN-06）：删除 `sts_training_attendance` 表、
  场次三个签到列、**空签到归档快照列**、签到 Java 资产、教师工作台签到统计与三个签到权限/菜单种子。
  替代口径：**线下完成只认教师录入的成绩**（`TrainingOfflineScore`）。
- `2026-09-21-add-archive-attendance-facts`：**目录为空**——曾计划补归档签到事实，最终未落地。
- `2026-09-21-remove-archive-attendance-prerequisite`：移除归档侧的**伪 `ATTENDANCE` 前置**。
  该 Change 明确写明"归档服务**无条件**把 `ATTENDANCE` 加入 `missingItems`……这是**遗留技术前置，
  不是既定业务规则**"，业务基线声明为"评分决定线下培训完成，不需要签到、签退、扫码、定位或现场证据"。

**关键点**：那次清理的**非目标**明确写了
"**不新增任何签到实体、表、接口、权限、页面、扫码、定位、签退、图片证据或移动端流程**"。
因此后续若要加回签到或影像证据，**必须显式修订该条款**，不能当作从未说过。

### 2.4 结论与待确认

签到的**业务必要性来自甲方功能项，且原文不可改**；但它当前**没有数据来源**。
三条可选路径：

| 路径 | 做法 | 代价 |
|---|---|---|
| A. 恢复签到 | 重开 Change 恢复签到表/接口/权限，按功能项 44 落入档案 | 需先由甲方确认"签到方式和有效条件"（FR-LRN-009 遗留问题）；推翻 TRAIN-06 的清理 |
| B. 用线下场次状态替代 | 以 `TrainingOfflineSession.sessionStatus` 表达到场（需新增"场次参与"事实） | 语义弱于签到，需甲方认可"到场"口径 |
| C. 用影像记录承担证据职能 | 现场影像证明培训真实发生，档案"签到情况"与"影像记录"同期补齐 | 仍需甲方确认是否接受以影像替代签到 |

**建议**：把 A/B/C 三选项连同"功能项原文不可改"这一约束，一并向甲方确认。
在第 2.4 节结论落地前，档案的"签到情况"栏**不应伪造，也不应写空快照**，
应如实呈现为"未采集"并在 `missingItems` 以外单独说明。

**注意**：本期发现的前端丢弃，源于 `docs/api/archive.openapi.json` 中 `ArchiveViewVO`
**只声明了 9 个字段**，而 Java VO 里有 `plan / organization / participants / scores /
rewardPenalties / attachments` 六个字段未进契约。契约是唯一机器可读来源，故这是**契约收窄**而非代码缺陷，
补齐须同步 OpenAPI、VO、前端类型与页面，属 L4。

## 4. 档案文件格式：最小闭环决策

现状：
- 一期档案 `generatedFileStore.store(toJson(view), "archive-<planCode>.json", "application/json", "json")`；
- 个人档案 `openPersonFile` 即时 `toJson(person)` 拼 `.json`，不落库；
- 企业档案**无下载端点**（`archive.openapi.json` 仅 6 个操作）。

**按最小闭环取 PDF 单文件正本**：

- 用 **PDFBox 3.0.5 生成档案正本 PDF**（依赖已在 `sts-service-admin/pom.xml`，**无需新增依赖**）；
- PDF 内容含表头、培训计划信息、参训人员与成绩表、奖惩、综合评价、统计汇总与归档落款；
- **影像与附件以清单形式呈现**（名称、类型、上传时间、来源），原件**不进档案文件**，
  走各自受控下载端点；
- **不做 ZIP 档案袋**：打包影像原件超出 M4 最小闭环，且需要先完成 `sts_archive_asset` 接线。

**待确认**：若甲方要求档案文件**本身携带**影像/附件原件，则需升级为 ZIP 档案袋方案。

## 5. 企业档案口径：明确忽略跨租户

按文祥 2026-09-24 指示：**企业档案保持当前租户口径，不改动系统架构边界**。
功能项 44 中"包含所有企业的档案"按"**当前租户内所有企业**"理解并记录，不再作为偏差项跟踪。

同时确认：企业档案仍需补 **`enterprises/{trainingPlanId}/file` 下载端点**（功能项明写"培训结束后可用于下载档案文件"），
以及前端补齐 `trainingTypeId` 与起止时间筛选（后端 `ArchiveEnterpriseQuery` 已支持，前端未暴露）。

## 6. 推进顺序建议

文祥原设想"先补影像 → 再补三子项"。**方向正确（上游先行），但需要插入一步契约定界**：

1. **第一步：先定档案事实的字段边界（契约）**。这是上游和下游的共同输入。
   若先做上游、后定契约，上游可能产出档案用不上的字段；若先做下游，则必然又写空快照。
   产出：`archive.openapi.json` 的 `ArchiveViewVO` / `ArchivePersonVO` 字段清单 + 每个字段的数据来源。
2. **第二步：补上游数据源**（并行可行，不同域）：
   - 影像/附件：前端补上传与展示（`plan/workspace` + `PlanProcessResultsPanel` 附件页签恢复），
     后端已有 CRUD 复用；归档时写入 `sts_archive_asset`；
   - 签到：取决于第 2 节甲方决策，未定前不实施。
3. **第三步：补齐档案组装与前端展示**：`reward_penalty_snapshot` / `certificate_snapshot` 写真实事实，
   前端消费新契约字段，新增个人档案详情页与证书入口。
4. **第四步：档案文件改 PDF 正本**，并补企业档案下载端点与筛选项。

## 7. 需人工确认项

1. **签到口径**（第 2.4 节 A/B/C 三选一）——需甲方确认，因 FR-LRN-009 遗留"签到方式和有效条件待确认"。
2. **是否接受影像作为培训真实性证据**，以及是否修订 `remove-archive-attendance-prerequisite` 的
   "不新增图片证据"非目标条款。
3. **档案 PDF 是否需携带影像/附件原件**（决定 PDF 单文件 vs ZIP 档案袋）。
4. **个人档案"查看下载证书"的关联口径**：按 `TRAINING` 来源证书，还是包含该人在该培训内获得的全部证书。
5. **数据统计的最小口径**：需要哪些指标才算满足功能项"数据统计"。

以上均属 L3/L4，须先开 OpenSpec Change 并取得确认后再实施。

### Change B：`2026-09-24-close-training-archive-loop`（已开，待人工确认）

- delta 落点：`specs/m4-minimum-closure/spec.md`（ADDED，档案需求的唯一归属能力，不新建平行能力）。
  `openspec validate --strict` 通过。
- 范围（覆盖本项目第 3、4、5 节）：档案事实组装与 `archive.openapi.json` 扩展、
  `reward_penalty_snapshot` 与 `certificate_snapshot` 写实、`sts_archive_asset` 接线、
  **线下成绩映射为签到情况**、统计口径、档案文件改 **PDF 正本**、个人档案详情页与证书入口、
  企业档案筛选与每期档案下载。
- 关键实现结论（写代码时直接用）：
  - **契约刻意收窄是主因**：后端 `buildView` 已给 `plan/organization/participants/scores/rewardPenalties/attachments`，
    但 `archive.openapi.json` 只声明 9 个字段、前端 `ArchiveView` 只有 8 个 → 必须契约先扩，否则前端永远看不到。
  - **PDFBox 3.0.5 在依赖里，但全仓只用于「读/规范化 PDF」**（`asset/transcode/PdfPageCounter`、
    `PdfPageTreeNormalizer`），**没有任何生成文本 PDF 的代码**；**仓库零字体资源**（无 ttf/otf/ttc）。
    → 采纳「AWT 绘页（沿用 `CertificateImageRenderer` 的逻辑字体路径）+ PDFBox 装载图像页」，
    零新依赖、零新字体资源；代价是文本不可检索。若要可检索文本 PDF，须另开 Change 引入 CJK 字体资源。
  - 签到映射三态：`NOT_APPLICABLE`（计划无线下内容）/ `SIGNED`（已录入线下成绩）/ `NOT_RECORDED`；
    为查询期派生字段，**不落库、不进 `missingItems`**、不新增签到表。
  - 架构一致性：`sts_archive_asset.asset_type` DDL 注释含 `IMAGE/VIDEO`，`uk_version_file` 唯一键就位
    → 接线**不需要迁移**；`sts_archive_participant` 六类快照列齐 → 写实也**不需要迁移**。
