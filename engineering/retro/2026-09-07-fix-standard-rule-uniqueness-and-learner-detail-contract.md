# Retro：培训标准基础规则唯一性与学员详情契约修正

## 做得好的地方

- 联调清单先审核再实施：只做后端必须保证的唯一性，以及契约与真实 JSON 对齐，没有把计划上的培训性质搬到标准。
- 唯一性校验放在乐观锁更新和软删之前，失败不会消耗版本或清掉旧规则。

## 问题

- 标准基础规则长期只在前端限制条数，后端按 max/逐条校验也能“碰巧”工作，脏数据要到计划发布才难查。
- 学员详情 OpenAPI 把嵌套 VO 写成 string，example 也是「示例值」，调用方无法按契约生成类型。

## 原因

- 规则表要同时容纳可重复的指定资源规则，没有对 `TOTAL_HOURS`/`ONLINE_RATIO` 做服务层单值约束。
- 契约生成时未展开嵌套类型，后续改 VO 没有回写 schema。

## 改进

- 前端已当作正式规则的基数约束，必须在保存和发布两个入口由后端重复校验。
- 修改对外 VO 时按 Controller 对照 OpenAPI 的 `$ref`、required 和 example，禁止残留 string 占位。
