## 2026-10-09 续办（第三批：T1 业务关闭 + T2 改密补验 + 整批收口）

- **「环境阻塞」必须区分「策略阻断」和「依赖掉线」**：T2 改密上一轮记为「被敏感内容策略阻断」，复盘时核对日志才发现真实根因是共享开发库 `19.191.192.146:8045` 连接超时（`ERROR 2003 (10060)`）。教训：不要把「执行被前置检查拦下」笼统归因为策略问题，要看脚本退出路径与后端异常；写类验收脚本一律先做「前置可登录」检查，失败即不改数据退出——这次正是它避免了在库不可用时误改凭证。库恢复后同一脚本一次通过（10 PASS / 0 FAIL），说明**阻塞项的成本几乎全在等待依赖，而非实现**。
- **异步/定时能力要用真实调度器取证，不要用单测代替**：截止提醒的窗口逻辑单测早已覆盖，但真正有说服力的证据是「把真实任务的截止时间挪进窗口 → 等真实 `@Scheduled` 扫描 → 消息表真的多出对应条目 → 再等一轮不重复 → 还原」。三步（负例/正例/幂等）+ 回滚，才是可复核的闭环。
- **隔离样本优于改既有数据**：培训生命周期没有用库里现成的 RUNNING 计划（cancel 会连带改参训人结果状态、触发学时预警刷新），而是**新建带时间戳的临时计划 + 参训人**，跑完整体删除；课程上下架只挑状态字段可精确还原的 `offline`（不改版本行）。教训：能造干净样本就不要动共享业务数据，能选单向操作就不做双向。
- **失效语义要落到「打开业务给出明确原因」**：只证明「通知还能查到」不够，必须真取一次业务接口。本轮 `GET /training/learner/participants/{id}` 返回 **8155「培训任务对当前学员不可见」**，才是「解释失效或权限原因」的实证。
- **Windows/GBK 两个反复踩的工具坑**：① Node `execFileSync`/`spawnSync` 起 `mysql.exe` 会偶发 `EBUSY`（与并发无关，重试也不稳），正解是**bash 跑 mysql、Node 只做 HTTP** 分工；② 终端 GBK 而库内容 UTF-8，直接比对中文会**假阴性**，断言中文一律 `HEX(...)`。这两条让「脚本报 FAIL」两次都是脚本问题而非产品问题，耗掉不少排查。
