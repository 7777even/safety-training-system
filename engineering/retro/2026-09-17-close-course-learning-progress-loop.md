# Retro：课程学习进度上报闭环与完成阈值生效

## 根因

表象是「学员学习进度表大量字段显示 `--`、有效学习时长长期为 0、管理员配的学习时长不生效」。根因分两层：

1. **结算与上报的驱动方式错配**。客户端计时模型是「事件驱动结算（`syncStudyClock()`）+ 时间驱动上报
   （心跳 `setInterval` 30 秒）」。`syncStudyClock()` 的调用点只有可见性变化、媒体播放/暂停、切换内容项三类事件；
   纯文档类内容项（PDF 等）既没有媒体事件，用户不切标签页时也没有任何事件，
   于是心跳读到的是**尚未结算的空累计值** ⇒ `validStudySeconds` 恒为 0。
2. **管理端阈值字段没有消费点**。内容项 `minimumStudySeconds` 与材料规则 `durationMode` 只出现在
   DTO / Entity / 快照 / VO / DDL，后端没有任何业务逻辑读它；而 `resolveRequiredSeconds()` 在阈值缺失时返回 0，
   `maybeCompleteItem()` 随即判定 `studySeconds >= 0` 成立 ⇒ **首次上报即完成**。

更上游的原因在规格侧：`openspec/specs/` 下没有覆盖「学习会话上报与内容项完成判定」的能力规格，
这些规则只散落在已归档 Change 的 design 里，缺少可追溯的 MUST 约束，字段长期失效才没有被发现。

## 修正

- 把结算点收敛到**上报点**上（`reportCurrentSession()` 取值前先 `syncStudyClock(now)`），
  而不是逐个事件补调用。这样心跳、切换内容项、页面卸载、媒体自然结束四条路径统一先结算，
  结算点与上报点重合后「清零累计值 + 重置区间起点」天然衔接，既不重复也不遗漏。
- 阈值改为三级解析（自定义材料规则要求秒数 → 内容项最低学习秒数 → 材料规则机构默认值），
  判「是否自定义」只能看快照 `materialRule.source`：ASSET 的 `materialRule` 永远非 null（后端会兜底
  15 秒默认规则），「有值即覆盖」会把内容项门槛挡掉。第三档必须保留，否则未配置阈值回 0，
  又退回「首次上报即完成」的旧缺陷。
- `durationMode` 明确定义为退役字段：管理端删设置项、后端不再校验必填、留空补 `AUTO` 落库；
  DB 列保留不加 migration，不为一个已废弃字段引入不可回退的 DDL。
- 把上报、有效时长结算、阈值解析与进度重算固化为 `course-learning-progress` 能力规格。
  本次复核发现该 delta 用 `## Requirements` 而非 `## ADDED Requirements`，严格校验不通过，已补正。

## 后续

- **媒体暂停不计入**（规格 Scenario「可计时媒体暂停期间不计入」）目前只有代码守卫：
  当轮环境没有视频素材与 `HLS` 派生产物（`sts_asset_asset` 只有 1 条 DOCUMENT），
  无法构造真实 HLS 播放场景，因此未做端到端。要真验需要一条可播放的 HLS 资产
  （上传视频 → 转码 → `sts_asset_derivative` 落 `HLS` 行 → 发布新课程版本），
  属需要人工确认的数据构造，未擅自执行。
- **两端「可计时媒体」判定口径不一致**：PC 用 `playInfo.format === 'hls'`，移动端用
  `assetType ∈ {VIDEO, AUDIO}`。正常转码路径下两者等价；只有在「视频素材缺 HLS 派生」的退化路径下分叉
  （PC 视为非可计时、移动端视为可计时），而该路径下两端都放不了，影响有限，建议后续统一。
- 心跳上报的 `endReason` 恒为 `USER_EXIT`，无法区分「周期检查点」与「用户退出」；
  用 `sts_course_study_session` 做时长对账时容易误读。
- 仍属延期项、本期未动：防快进 / 倍速限制 / 离页暂停计时 / 水印四个材料规则字段的客户端消费（功能项 75）；
  LIVE 内容项无完成路径；`creditAwarded` 恒为 0；学习进度表对文档类内容项的「最近位置 / 结束位置」列口径未调整。
