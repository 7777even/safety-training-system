# PC/H5 PDF 渐进预览 Retro

日期：2026-08-14  
Owner：AI（前端）

## 做得好的地方

- 将 PDF 从通用文件查看器中拆出，保留非 PDF 插件链，避免扩大重构范围。
- 共享无 UI 控制器统一了 PC/H5 的按页加载、任务取消和资源释放，并先用 TDD 固化关键行为。
- 删除不可维护的第三方 dist patch，恢复冻结锁文件安装。
- 使用真实 648 页样本验证 Range，而不是仅以代码参数推断网络效果。

## 发现的问题

- 原查看器不仅会创建全部页面 DOM，PC 还会在滚动时扫描全部页面位置；后端线性化无法解决这些前端 CPU/DOM 问题。
- 线性化只提供按区间读取条件，实际首屏读取量仍取决于 PDF 的 xref、页面树和共享对象布局。本次样本首屏仍读取约 34.5 MB，不能把“支持
  206”等同于“首屏一定只有几百 KB”。
- 移动 workspace 的 Uni 构建链存在 pnpm 严格隔离下的传递依赖解析基线问题；业务改动不应通过持续复制传递依赖来掩盖。

## 后续改进

- 在真实登录页面补做 PC Chrome/H5 Network、Canvas 数量和视觉验收后关闭 Change。
- 独立修复移动端 Uni/Vite 依赖解析与 TypeScript `ignoreDeprecations` 配置，再恢复标准 build/typecheck 命令。
- 若产品要求进一步降低特定大 PDF 的首屏网络量，应基于对象布局数据评估 PDF 生成/重写策略，不回退到前端全量 Blob 或非线性化兼容路径。

## 2026-08-15 补充

- 首轮结论过早把“Range 生效”和“没有全量下载”视为优化完成；后续必须分阶段记录 `loadingTask.promise`、目标页代理和渲染数据的实际传输量。
- 扁平 Page Tree 才是 648 页样本文档初始化读取约 34 MB 的决定性原因；前端参数和 qpdf 线性化不能代替 PDF 结构验收。
- Page Tree 分层后，同一样本初始化降至约 0.78 MB、第一页数据就绪约 1.37 MB，后续实施必须以该基准做自动化回归，不能只检查
  `qpdf --check-linearization`。

- 结构正确性与网络性能现已合并进同一个 648 页真实进程测试，避免后续只验证页数或只验证 qpdf 退出码。
