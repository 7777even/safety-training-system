# Retro：培训计划初培 / 复审性质与学时判定

## 做得好的地方

- 从功能项原文区分“培训类型”和“本次培训性质”，避免把工种类型名称当成初培/复审判断依据。
- 将发布校验、冻结快照和监管预警统一到 `applicableRequiredHours`，历史结果不会随来源配置改变。
- 真实验证同时覆盖旧库升级、空库 init、Entity 映射、混合计划发布和预警证据落库。

## 问题

- 初次 Flyway 测试夹具先删除了 seed 培训类型，导致历史计划插入语句没有数据源。
- 新增的预警 IT 两次遗漏已有非空 `description`，且最初按 JSON 原始文本断言，未考虑 MySQL JSON 规范化空格与数字格式。
- 完整 IT 才发现既有混合计划夹具的培训类型没有初培/复审学时。

## 原因

- 新业务约束加入后，部分旧测试夹具仍只满足旧数据库最低字段，而不满足新的发布业务前置条件。
- 对 MySQL JSON 的断言沿用了零 DB 字符串方式，没有第一时间采用结构化 JSON 比较。

## 改进

- 业务发布夹具应通过统一 helper 创建完整培训类型，明确初培/复审学时，避免不同 IT 各自遗漏字段。
- MySQL JSON 列一律解析为 JSON 节点后断言语义，不比较序列化空格、键序或数字尾零。
- 数据迁移夹具在删除 seed 数据前先建立需要保留的历史业务行，并明确断言插入行数或最终存在性。
