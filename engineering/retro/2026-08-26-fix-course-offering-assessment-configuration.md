# 开课配置与课程测验阅卷流程复盘

日期：2026-08-26

## 问题

- 草稿开课的考核执行对象需在保存阅卷人时创建，但前端提前读取批阅/结果，导致 7062 和无关的系统错误同时出现。
- `PageRequest<Void>` 与通用分页参数解析器不兼容，在 Java 21 模块限制下会触发反射异常。

## 改进

- 页面按开课状态决定可调用接口，草稿阶段只提供前置配置。
- 无筛选条件的分页接口也使用显式查询 DTO，禁止新增 `PageRequest<Void>`。
- 发布前置条件在创建流程内展示，并保留后端业务校验作为最终保障。
- 多课程测验使用章节卡片总览，避免因单项选择器隐藏其他测验的配置状态；测试必须覆盖“首项已配置、后项未配置”的顺序场景。
- 人员选择确认即为一次明确提交，应直接保存，避免在选择器与配置页之间增加无业务价值的第二次确认；版本资源选择器应按资源聚合后只保留当前可用版本。
- 课程作答即使底层复用考试快照，也必须保持课程 API 与独立考试 UI 路由隔离；否则独立考试倒计时会对课程作答产生错误副作用。
- 课程任务对外状态不能直接透传考试内部状态；`PENDING_REVIEW` 必须在课程边界收敛为“等待结果”，否则前端会误走继续作答分支并制造重复答卷。
- 课程自动生效结果不能复用独立考试“人工发布后才展示解析”的可见性判断；两类结果需要在同一读取服务中按来源类型显式分支并覆盖回归测试。
- 学员作答页的“提交”和“返回”均是数据丢失风险点，必须以最近成功暂存快照与当前答案比较后再继续操作。
