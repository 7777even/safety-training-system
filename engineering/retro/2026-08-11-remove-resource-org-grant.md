# 跨机构资源授权退役 Retro（2026-08-11）

## 做得好的地方

- 先用失败测试固定“其他机构资源必须拒绝”的边界，再删除授权服务和跨租户读取旁路，避免只删管理入口却保留隐式访问能力。
- 历史 migration 保持不可变，使用新的顺序 migration 清理角色菜单、菜单和数据表，并以真实 MySQL IT 验证破坏性结果。
- 同步更新当前 schema、菜单、OpenAPI、路线图和进度表，明确区分当前真相源与历史记录。
- 完整执行零 DB 与带 DB 测试，覆盖业务边界、租户 SQL、migration 和既有回归。

## 发现的问题与原因

- 资源授权同时渗透在课程、考试、培训、租户豁免、菜单、契约和文档中，仅删除 `com.sts.grant` 会留下可用旁路或错误说明。
- 历史设计与当前产品基线仍包含原始需求事实；若直接全文删除会改写审计历史，因此需要在当前基线增加退役声明并保留历史材料。
- 数据表删除不可逆，必须把部署前备份和应用版本回退条件写进验收记录，而不能把代码回滚等同于数据恢复。

## 改进

- 后续退役横切业务能力时，固定从“访问路径、管理入口、数据库、权限菜单、契约、当前文档、历史资产”七个维度做残余扫描。
- 对删除表或批量清理数据的 migration 固定增加真库 IT，并显式验证关联数据清理顺序。
- 当前能力说明与历史规格分开维护：当前文档直接陈述有效边界，历史 OpenSpec、migration 和 QA 仅作为审计记录保留。
- 前后端由不同 Git 身份协作时，在交付中显式列出未授权修改的一端，避免把后端退役误报为全端完成。
