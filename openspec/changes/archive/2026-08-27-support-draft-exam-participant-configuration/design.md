# Design：草稿考试人员配置与执行归属生命周期

## 1. 设计结论

`Exam` 继续表示管理员可编辑、可发布的独立考试任务；`AssessmentExecution` 继续作为 Candidate、Reviewer、Attempt
等事实的唯一执行归属。

为兼容“先配人员、后发布”的既有业务顺序，独立考试执行对象允许在草稿期因首次有效人员写入而提前物化。草稿期物化的对象只承担人员归属，
其中的快照字段是满足现有非空结构的预备投影，不具有已发布执行快照的业务权威性。发布事务必须在同一
`assessmentExecutionId` 上以最终考试数据完整覆盖快照并重算摘要；只有父级 `Exam.publishStatus` 进入 `PUBLISHED`
后，执行对象才可被学员任务、开考和正式执行链使用。

本 Change 不增加 `DRAFT` 执行状态。现有 `execution_status=READY` 仅表示执行记录已经物化且可承载归属，不能单独证明考试已经发布或允许作答。

## 2. 不变量

1. 一个未逻辑删除的独立考试最多只有一个未逻辑删除的执行对象。
2. Candidate、Reviewer 和 Attempt 只使用 `assessmentExecutionId` 作为执行归属，不恢复 `examId` 第二归属。
3. GET 请求不得创建、更新或删除执行对象及人员关系。
4. 草稿期执行对象不得绕过 `Exam.publishStatus`、考试开放时间和 Candidate 资格进入学员执行链。
5. 发布只能刷新原执行对象，禁止通过删除重建改变 `assessmentExecutionId`。
6. 发布冻结不增删 Candidate 或 Reviewer。
7. 发布成功后的快照不可再由草稿更新逻辑修改。
8. 非草稿考试缺失执行对象属于数据一致性异常，继续返回 `7062`，不得伪装为空配置。

## 3. 状态与接口行为矩阵

| Exam 状态   | 执行对象 | 操作              | 行为                               |
|-----------|------|-----------------|----------------------------------|
| 不存在       | 任意   | 任意人员接口          | 保持现有考试不存在错误                      |
| `DRAFT`   | 不存在  | `GET reviewers` | `200`，返回空数组，不写库                  |
| `DRAFT`   | 不存在  | 绑定解析结果为空        | 成功返回空结果，不创建执行对象                  |
| `DRAFT`   | 不存在  | 以空数组替换阅卷人       | 成功，无操作，不创建执行对象                   |
| `DRAFT`   | 不存在  | 首次写入非空考生或阅卷人    | 校验当前资源可形成执行预备投影，幂等创建执行对象并保存关系    |
| `DRAFT`   | 已存在  | 读取或保存人员         | 复用原执行对象，按既有唯一键幂等处理               |
| `DRAFT`   | 已存在  | 更新考试信息/策略       | 更新考试任务；最终权威快照由发布事务统一刷新           |
| `DRAFT`   | 已存在  | 删除考试            | 在同一事务内清理阅卷人、考生、执行对象、策略和考试        |
| `DRAFT`   | 有或无  | 发布              | 校验发布条件；创建或复用执行对象，刷新最终快照后发布       |
| 非 `DRAFT` | 不存在  | 人员读写            | 保持 `7062`，暴露数据一致性异常              |
| 非 `DRAFT` | 已存在  | 人员读写            | 保持当前接口行为和状态限制，不在本 Change 中新增锁定规则 |

## 4. 首次人员写入

### 4.1 考生绑定

处理顺序：

1. 读取并校验考试存在。
2. 使用现有人员选择服务解析为当前机构的具体用户 ID，并按现有规则去重。
3. 解析结果为空时直接返回空结果，不物化执行对象。
4. 解析结果非空时获取人员写入所需执行对象：
  - 已存在时直接复用；
  - 不存在且考试为 `DRAFT` 时幂等创建；
  - 不存在且考试非 `DRAFT` 时返回 `7062`。
5. 继续按 `assessmentExecutionId + userId + 既有业务上下文` 唯一边界写入具体 Candidate，并冻结人员档案快照。

### 4.2 阅卷人整体替换

1. 读取并校验考试存在。
2. 请求列表为空且执行对象不存在时，按“清空一个本来为空的集合”处理，成功返回且不创建对象。
3. 请求列表非空时按考生绑定相同规则获取或创建执行对象。
4. 在事务中按原执行对象整体替换 Reviewer；重复用户仍由请求校验或现有唯一约束阻止重复关系。

### 4.3 并发幂等

并发首次保存继续依赖现有 `uk_execution_exam_deleted` 唯一键收口。创建冲突方重新读取同一考试的现存执行对象，随后在人员唯一键下幂等写入，
不得生成第二个执行对象。并发整体替换阅卷人的最终集合仍遵循现有“后提交事务最终生效”语义，本 Change 不新增版本字段或并发令牌。

## 5. 草稿期预备投影

现有执行表的资源和快照字段均为非空，因此首次有效人员写入前必须能够从当前考试形成完整预备投影：

- 在线考试/专项练习必须具有可用的已发布试卷版本；
- 题库练习必须具有可用题库；
- 线下考试继续使用现有 `OFFLINE_RESULT` 投影；
- 当前考试行上的时长、及格分、题序、多选计分和策略必须通过既有校验。

资源尚不完整时保持现有资源错误码，不创建执行对象，也不写入部分人员关系。这样无需放宽数据库非空结构，也不在草稿表中引入第二套人员归属。

草稿更新不要求每次都刷新预备投影。原因是草稿允许继续换卷和修改规则，而预备投影不参与任何正式执行；频繁同步会让人员配置反向限制合法草稿编辑。
发布事务才是唯一必须成功的最终冻结边界。

## 6. 发布冻结

发布操作在一个事务中完成以下步骤：

1. 读取考试并执行现有状态、资源和发布条件校验。
2. 获取现有执行对象；不存在时幂等创建，存在时保留其主键。
3. 从最终 `Exam`、最终资源和最终 `ExamPolicy` 构造完整规范化快照。
4. 覆盖执行对象的来源、资源、时长、总分、及格分、题序、多选计分与策略快照字段。
5. 对规范化快照重算 SHA-256，并保存 `snapshotHash`。
6. 更新考试发布状态和发布时间。
7. 事务提交后，原 Candidate 与 Reviewer 因执行对象 ID 未变化而自然保留。

任何一步失败必须整体回滚，不能出现考试已发布但快照仍旧、快照已更新但考试未发布，或人员关系被清空的中间结果。

### 6.1 摘要边界

摘要输入使用字段顺序稳定的规范化 JSON，至少包含：

- `sourceType`、`sourceBusinessId`、`assessmentKind`；
- `resourceType`、`resourceId`、`resourceNameSnapshot`；
- `durationSecondsSnapshot`、`totalScoreSnapshot`、`passScoreSnapshot`；
- `questionOrderModeSnapshot`、`multiSelectScoringSnapshot`；
- 仅包含业务生效字段的策略快照。

人员关系、数据库主键、审计字段、逻辑删除值、乐观锁版本和更新时间不进入摘要。由此，同一份业务快照可得到稳定摘要，人员调整不会伪装成试卷或规则变化。

## 7. 读取语义

`GET /api/exam/exams/{examId}/reviewers`：

- 先保持现有考试存在性和数据范围校验；
- 草稿考试无执行对象时返回成功空数组；
- 有执行对象时按该对象查询 Reviewer；
- 非草稿考试无执行对象时返回 `7062`。

接口路径、权限 `exam:exam:list`、响应数组结构和成功外壳均不变化，只更新 OpenAPI 对草稿空读和 `7062` 适用条件的描述与
example。

## 8. 草稿删除

提前物化执行归属后，草稿删除必须扩展为一个业务级清理事务：

1. 保持“仅 `DRAFT` 可删除”的现有护栏。
2. 若不存在执行对象，沿用现有策略与考试删除路径。
3. 若存在执行对象，先确认不存在 Attempt；草稿执行链按不变量不应产生 Attempt，若存在则拒绝删除并报告一致性异常。
4. 按引用顺序清理 Reviewer、Candidate 和 AssessmentExecution，再删除策略与考试。
5. 使用各实体既有的物理删除或逻辑删除机制，不改变数据库结构和历史表语义。

删除后再次使用同一业务编码创建考试时，不得被旧的活动执行对象或人员唯一键阻塞。

## 9. 权限、机构与安全边界

- 不修改 Controller 路径和权限注解。
- 执行对象机构 ID 只从受信任的 Exam 派生，不接受请求传入。
- 人员选择继续限制为当前机构可用人员。
- 学员任务、开始作答和批阅任务查询继续同时校验业务来源、执行归属和既有权限。
- 草稿执行对象的提前存在不得使考试出现在学员任务中，也不得允许开始作答。

## 10. 数据与契约影响

- **数据库**：无表、字段、索引、约束或初始化数据变化；不新增 migration。
- **API**：路径、Method、字段、状态码外壳和权限不变；`reviewerUserIds` 仍必传但从非空数组调整为允许空数组，空数组表示清空；同时收窄
  `7062` 的适用条件并补充草稿空读描述。
- **兼容性**：已发布且执行对象正常的数据无迁移；已发布但缺执行对象的数据仍通过 `7062` 暴露，不做读取时自动修复。
- **前后端影响**：仅后端；前端以 OpenAPI 为准另开。

## 11. 测试设计

### 11.1 零 DB（先失败后实现）

1. 草稿无执行对象读取阅卷人返回空数组，且 Mapper 无写调用。
2. 不存在考试仍返回既有错误。
3. 非草稿无执行对象仍返回 `7062`。
4. 首次非空考生绑定创建执行对象并写入 Candidate。
5. 首次非空阅卷人替换创建执行对象并写入 Reviewer。
6. 空选择、空阅卷人首次保存不创建执行对象。
7. 重复保存复用同一执行对象，不重复创建人员。
8. 草稿更新后发布，以最终试卷、规则和策略覆盖原预备投影并重算摘要。
9. 发布刷新不改变执行对象 ID，不删除 Candidate/Reviewer。
10. 发布中任一步异常时事务方法抛错，考试不得进入成功发布结果。
11. 删除带人员配置的草稿按引用顺序清理；异常 Attempt 阻止删除。
12. 学员开始入口仍拒绝未发布考试，不能只凭执行对象存在开始作答。

### 11.2 MySQL IT

1. 并发或重复首次创建最终只有一个活动执行对象。
2. Candidate/Reviewer 在发布快照更新后仍指向原 `assessmentExecutionId`。
3. 最终快照字段与 hash 真实更新落库。
4. 草稿删除后无活动执行对象、Candidate 或 Reviewer 残留，相关唯一值可按既有规则复用。
5. 整体替换阅卷人与发布失败时的事务回滚符合预期。

## 12. 取舍

### 采用：草稿期按需物化唯一执行归属，发布时最终冻结

优点是无需改库或建立第二套人员表，且 Candidate/Reviewer 从创建起就遵守最终归属模型。代价是必须明确区分“记录已物化”和“考试已发布”，所有执行入口不能只看执行对象是否存在。

### 不采用：GET 时自动创建

违反查询无副作用原则，并会让页面探测产生孤立数据。

### 不采用：恢复 Candidate/Reviewer 的 `examId` 草稿归属

会建立第二套归属和发布迁移过程，违反统一执行对象设计，并需要数据库变更。

### 不采用：先发布再配置人员

与功能项 16 和既有考试安排流程相反，也会让无人员考试短暂进入已发布状态。
