# 建立项目知识库基础资产设计

## 设计原则

1. `docs/` 只沉淀跨版本有效的长期共识；需求变更仍以 `openspec/` 为唯一规格来源。
2. 文档按业务领域组织，不按 PC、移动端或后台页面组织。
3. 领域模型停留在概念层，描述对象、关系和业务语义，不形成数据库结构设计。
4. 同一业务概念在角色、模块、流程、领域模型和术语表中使用同一名称。

## 角色协作模型

- 园区监管端：制定培训标准和类型、管理受监管机构、监测数据并生成监管预警。
- 企业/培训机构端：准备教学资源、制定并执行培训计划、组织课程与考试、形成分析、档案和证书。
- 学员端：接收培训任务、完成学习与考试、查看个人档案并获取证书。

企业端与培训机构端本阶段共用能力模型；两者是否具有不同的数据隔离、授权链路和业务规则为“暂定”。

## 业务闭环

1. 园区监管端制定培训标准与数据规范，并下发可采用的培训类型或模板。
2. 企业/培训机构端基于标准和资源制定培训计划，配置课程、考试和人员范围。
3. 学员接收任务，完成课程学习、仿真练习（暂定）或线下培训记录。
4. 学员参加理论或仿真考试（暂定）；企业/培训机构完成自动判分和人工批阅。
5. 系统形成成绩与考情分析，沉淀个人、企业/机构和期次档案。
6. 满足规则时生成并下发证书；监管端汇聚计划、学习、成绩和档案数据进行监控与预警。

## 风险与取舍

- 附件包含较多功能细节，但本 change 仅建立知识基线；细化业务规则必须另建对应 OpenSpec change。
- 培训标准、学时、合格线、证书签发条件和预警阈值均不在本次确定，文档统一标记为“暂定”。
- 数据模型不提前落表，避免在缺少 API、权限和生命周期确认时固化错误结构。
