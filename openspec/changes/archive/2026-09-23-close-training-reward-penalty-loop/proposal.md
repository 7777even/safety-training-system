# Proposal：补齐培训计划奖惩业务闭环

## 状态

- 已获人工确认：按既有计划内奖惩接口实施，后端校验执行中状态、参训人归属和结束冻结；从奖惩 HTTP 接口、培训成果回读及 PC 工作台操作验收。
- 2026-09-24 已获人工确认：补齐计划奖惩佐证预览，新增按奖惩记录读取佐证的受控接口，不开放按任意文件 ID 读取。
- 2026-09-24 已获人工确认：说明和发生日期保持现有可选契约，通过迁移将奖惩表两列改为允许空值。
- 功能项依据：`docs/product/功能项.csv` 中山 36「支持上传培训过程中产生的影像、培训附件、奖惩评价、综合评价等资料」、39「根据奖惩或考试成绩自动计算得分」、40「已结束的培训结果包含奖惩信息」、44「个人/企业/一期档案包含奖惩记录」。

## 现状与问题

- `training.openapi.json` 已公开奖惩查询、创建、更新、删除和现有 `training:reward:*` 权限；PC 工作台只读取，过程页奖惩区域被注释，管理员无法在计划内录入。
- `TrainingRewardPenaltyServiceImpl` 写入时未校验计划状态、参训人是否属于该计划，也未在更新/删除时阻止已结束结果被改写。前端隐藏按钮无法保护直接调用接口。
- 奖惩写入已触发参训结果同步，但缺少「录入 → 综合分刷新 → 结束冻结 → 成果/档案回读」的真实角色证据。

## 目标与边界

1. 管理员在执行中的计划内，对本计划参训人维护奖励/处罚记录；已结束计划和成果、档案只读。
2. 服务端在新增、修改、删除前核实计划与参训人的归属、计划状态和记录归属，拒绝跨计划、跨机构和结束后的修改。
3. 沿用已有接口、权限和数据表；复用已有文件上传能力处理可选佐证，不引入奖惩规则引擎、审批、批量导入或独立菜单。
4. 奖惩变动后沿用现有参训结果同步；结束后结果与归档事实保持冻结，不由页面重算分数。

## 实施顺序

- Task 1：后端写入校验、既有错误契约和定向回归。
- Task 2：PC 计划内奖惩区域与四项操作。
- Task 3：数据库、接口与真实登录态纵向验收，Review、QA、Retro 和状态同步。
