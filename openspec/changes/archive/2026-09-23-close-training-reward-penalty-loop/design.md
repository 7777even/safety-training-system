# Design：计划内奖惩最小闭环

## 业务路径

管理员进入执行中的培训计划 → 「过程与结果 / 奖惩」选择本计划参训人 → 新增奖励或处罚 → 服务端校验并保存 → 自动刷新该参训人的综合分 → 管理员回看列表和分项结果 → 结束培训后只读 → 培训成果与档案展示同一奖惩事实。

## 后端

- 在既有 `TrainingRewardPenaltyServiceImpl` 的写入路径校验：计划存在且属于当前机构、状态为 `RUNNING`；参训人存在且属于该计划及当前机构。更新、删除以记录保存的计划/参训人为准复核，不接受页面传入另一组关联 ID。
- `scoreChange` 沿用现有有符号分值语义：正数加分、负数减分，`0` 是有效值，空值仅记录事实不改变分数。奖励/处罚与分值符号保持一致。`status=0` 的记录保留但不计入当前综合分。
- 更新沿用 `version` 乐观锁；校验或写入失败不得触发结果同步。成功后在同一事务内沿用既有 `synchronizeParticipant` 入口，不另外创建计算批次。
- 计划结束与奖惩写入存在并发时，应以计划终态禁止晚到写入为准；采用当前事务与锁机制的最小实现，并用 MySQL IT 验证。已有 404/409 错误结构继续使用；新增具体业务码时同步 OpenAPI 与测试。
- 可选佐证文件沿用既有 `evidenceFileId`，须由当前机构可访问的已上传文件获得，不允许客户端任意引用他人文件。

## PC 交互

- 在计划工作台第 5 步「过程与结果」恢复奖惩列表，按权限展示新增、编辑、删除；仅 `RUNNING` 允许写操作。计划 `ENDED` 时只读。无独立奖惩菜单。
- 表单直接从本计划参训名单选择人员，不输入 ID。字段来自现有契约：类型、标题、说明、分值变化、发生日期、可选佐证、状态。新增默认启用；更新从详情回显 `version`。所有字段和状态使用中文提示。
- 删除前确认；成功后刷新奖惩列表与该参训人的结果。成果页和档案沿用既有只读查询，不在前端重新计算综合分。后端拒绝时显示中文业务消息并保留当前表单输入。

## 数据与契约影响

- 无新业务表或菜单。新增 `GET /api/training/reward-penalties/{rewardPenaltyId}/evidence`，沿用 `training:reward:list`，按当前机构可见的奖惩记录定位佐证文件，返回原始字节及内联文件名；无记录或无可读佐证返回 404，不提供任意文件 ID 下载入口。列表和编辑弹窗通过该接口预览已保存佐证，新上传尚未保存的佐证直接预览本地文件。
- 奖惩说明和发生日期沿用现有可选契约，分别将 `sts_training_reward_penalty.description` 与 `occurred_date` 改为可空；同步 Admin init 快照、增量迁移和 schema 版本。Entity 已对两字段使用 `FieldStrategy.ALWAYS`，无需新增字段或修改请求形状。
- 不顺带恢复已延期的签到、审批、手工综合成绩批次或通用人员奖惩档案。
