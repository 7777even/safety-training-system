# 设计：持久化且隔离的浏览器登录会话

## 推荐方案：持久化会话槽位 + 标签页绑定

浏览器端维护一个 `localStorage` 会话槽位集合，而不是保存单个全局 Token：

```text
sessionSlots = {
  slotId: {
    token,
    userSummary,
    lastUsedAt,
    expiresAt
  }
}
```

每个标签页只保存一个不含敏感信息的 `tabId`，并绑定到一个 `slotId`。`tabId` 使用 `window.name` 保存，首次打开时随机生成；Token 只保存于对应的会话槽位中。

## 打开与恢复流程

1. 标签页启动时读取自己的 `tabId`。
2. 如果该 `tabId` 仍绑定有效会话槽位，直接恢复该账户。
3. 如果没有绑定，显示“选择登录会话”：可选择已有账户槽位，或创建新槽位并登录。
4. 同一槽位已被其他标签页占用时，提示用户选择其他槽位或确认接管；默认不自动抢占，避免两个标签页再次互相覆盖。
5. 登录成功后只更新当前绑定的槽位。

这样，浏览器重启后即使标签页身份无法被浏览器恢复，用户也可以从已保存的账户槽位中恢复会话，无需重新输入密码；不同标签页可选择不同槽位。

## 退出、切换与清理

- 退出登录：只清理当前标签页绑定的槽位 Token，并解除当前标签页绑定；其他槽位不受影响。
- 切换账户：先解除当前绑定，再选择其他未占用槽位；不覆盖其他槽位。
- 账户槽位增加 `expiresAt`，过期后不可恢复并在下次启动时清理。
- 提供“移除已保存账户”操作，删除对应槽位及其 Token。
- 不通过 `storage` 事件广播登录状态；跨标签页通信仅用于发现槽位占用状态，不传 Token。

## 安全与取舍

- 持久化 Token 仍存在 XSS 风险；继续依赖现有前端安全边界，不能声称比当前 Token 存储更安全。
- `window.name` 只保存随机标识，不保存账户名、Token 或权限信息。
- 浏览器清理站点数据后无法恢复是预期行为。
- 使用“槽位选择”处理浏览器重启后的标签页身份不确定性，比依赖浏览器是否恢复 `sessionStorage` 更可靠，但首次恢复可能多一步选择账户。
- 暂不实现自动刷新 Token；若服务端 Token 过期，当前槽位需重新登录。

## API、权限与数据影响

- API：不变，继续使用现有登录、退出和当前用户资料接口。
- 权限：不变，每个请求只使用当前标签页绑定槽位的 Token。
- 数据库：不变。
- 后端：不变。

## 测试设计

- 两个标签页分别绑定槽位 A/B，登录后请求分别携带 Token A/B。
- 当前标签页切换或退出槽位 A，不影响槽位 B。
- 浏览器重启模拟后，可从持久化槽位恢复账户而无需重新输入密码。
- 已占用槽位不能被另一个标签页静默抢占。
- 过期槽位和移除槽位不会恢复。
