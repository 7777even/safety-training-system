# Design：培训计划评价表单绑定保存时对齐既有约束

## 1. 校验顺序

`PUT /api/training/plans/{id}/evaluation-forms` 在乐观锁更新之前完成业务校验，失败不消耗版本、不删除既有绑定：

1. 计划存在且为草稿。
2. `forms` 按 `usageType` 去重；重复则 HTTP 409 / `8133`，「同一评价用途只能绑定一个表单」。
3. 每条：版本存在且 `PUBLISHED`，否则 400 / `8110`（保持既有码）。
4. 通过版本加载表单主体：必须存在、`organizationId` 等于计划机构、`status = 1`；否则 400 / `8134`，「评价表单不属于当前机构或不可用」。
5. 按请求 `version` 更新计划；失败 409 / `8104`。
6. 主键值软删除旧绑定，插入本次全量。插入若仍撞 `uk_plan_usage_deleted`，捕获后转为 409 / `8133`。

`forms` 为 `null` 时按空列表处理；空列表跳过 2～4 的条目校验，执行 5～6，即解除全部绑定。

## 2. 与发布预检对齐

发布预检 `8128` 已检查机构与启停。绑定保存使用独立码 `8134`，因为这是写请求的直接失败，不是预检 issue
列表。口径相同：主体缺失、跨机构、禁用，同一消息。

不在绑定入口校验 `formType` 与 `usageType` 是否匹配。

## 3. 契约

- 操作 description 补充 `8133`/`8134`，并写明空数组解除全部绑定。
- `forms` 字段 description 明确空数组语义。
- requestBody 同时给出非空绑定与 `forms: []` 的 example。

## 4. 测试

零 DB：重复用途、跨机构/禁用表单在更新前失败；空数组仍走主键值软删除。不跑 IT（无表结构变化）。
