# Proposal：补齐培训档案事实与可交付档案文件闭环

## 状态

- **待人工确认。**
- 承接 `2026-09-24-close-training-material-loop`（培训资料/影像上传与受控读取闭环）。本 Change 只做**档案侧**：档案事实组装、归档快照写实、资料接线、档案文件格式、三视角展示补全。
- 功能项依据：`docs/product/功能项.csv` 功能项 **44**（一个单元格，含三个子项）：
  - **（1）个人档案**："建立培训个人档案及记录个人培训。支持查看个人档案详情页、支持导出档案记录、查看下载证书；档案详情内容包含个人培训记录、参训情况、奖惩记录及综合评价。"
  - **（2）企业档案**："包含所有企业的档案，可通过企业名称进行搜索查询；档案包含该企业下所有培训计划列表，可通过培训名称、培训编号、开始时间、结束时间或培训类型等信息筛选；支持查看企业档案培训详情，详情页可查看培训计划、参训人员、签到情况、学员成绩、奖惩、影像记录、附件及数据统计等信息；支持更新档案，在培训结束后，可用于下载档案文件。"
  - **（3）一期一档**："展示已完成的培训档案，档案内容数据来自于所有已完成的培训，培训计划列表展示所有已结束的培训；培训档案内容包括培训计划、企业列表、参训人员、签到情况、学员成绩、综合评价、奖惩、影像记录、附件、数据统计等信息。"
- 规格依据：`openspec/specs/m4-minimum-closure/spec.md`「档案必须提供个人、企业和一期三个视角」MUST 在三视角展示**一致**的计划、人员、成绩、评价、奖惩、影像、附件和统计事实，且 MUST NOT 写空快照。

## 现状与问题

- **契约刻意收窄，后端给的事实被整体丢弃**：`ArchiveServiceImpl.buildView` 已组装 `plan/organization/participants/scores/rewardPenalties/attachments`，但 `docs/api/archive.openapi.json` 的 `ArchiveViewVO` 只声明 9 个字段，前端 `ArchiveView` 只有 8 个 —— 页面因此只剩编号、名称、企业、人数。属**契约收窄**而非缺陷，补展示必须动契约（L4）。
- **归档快照写空**：`createFromPlan` 把 `reward_penalty_snapshot`、`certificate_snapshot` 硬编码写成 `"{}"`，正是规格禁止的"写空快照"。
- **影像/附件资产表零引用**：`sts_archive_asset`（`asset_type` 含 `IMAGE/VIDEO`、`source_attachment_id`、`uk_version_file`）与 `ArchiveAssetMapper` 全仓无写入，档案的"影像记录、附件"事实无处落。
- **档案文件是纯文本**：一期走 `generatedFileStore.store(toJson(view), "archive-<planCode>.json", "application/json", "json")`，个人档案在 `openPersonFile` 现拼一个 `.json`；契约也把两个 `/file` 响应声明为 `application/json`。这不是可交付文档。
- **企业档案缺口**：`listEnterprise` 只查当前租户**单个**机构，前端只暴露计划名称/编号两个筛选（后端已支持类型与起止时间，未暴露）；列表无任何档案文件下载入口（功能项明写"培训结束后可用于下载档案文件"）。
- **个人档案无详情**：前端只渲染一行表（编号/名称/企业/是否完整），无个人培训记录、参训情况、奖惩、综合评价，也**没有证书入口**（功能项明写"查看下载证书"）。
- **签到情况的原文与实现冲突**：功能项企业档案与一期一档两处都要求"签到情况"，而规格 MUST NOT 要求签到，且 `2026-09-10` 起签到表、场次签到列、归档签到快照列、权限与菜单已整体删除。

## 已确认口径（2026-09-24 文祥确认）

1. **签到情况以线下成绩录入为准**：教师能给学员录入线下成绩即视为该学员在线下培训到场；**不新建签到表、不恢复签到采集**，档案的"签到情况"由线下成绩事实映射呈现。
2. **统计口径**：培训内容、参训人数、整体学员完成情况，以及能反映培训情况的数据指标（见 design「统计指标口径」）。
3. **档案文件按最小闭环实现**：一期一档与个人档案出 **PDF 正本**；影像与附件在档案内以**清单**呈现，原件经受控端点另行获取，**不做 ZIP 档案袋、不内嵌原件**。
4. **个人档案证书**：提供证书清单与下载入口，**复用既有证书查询与文件端点**，不在档案里复制证书文件、不新签发证书。
5. **企业档案"所有企业"不跨租户**：按**当前租户内所有企业**理解，该偏差项关闭，不改动多租户边界。

### 补充确认（2026-09-24 第三轮）

6. **光栅 PDF 的文本不可检索：接受**——不引入 CJK 字体资源，将来需要可检索文本时另开 Change。
7. **证书清单受权限门控**：调用方缺少 `certificate:cert:list` 时，档案响应 MUST NOT 返回证书清单字段（不是"返回清单但禁用下载"）。
8. **历史 JSON 档案在页面标注**：提示"需重新更新档案以获得 PDF"；**不迁移历史文件**。

## 规格冲突与修订

- **修订**：`2026-09-21-remove-archive-attendance-prerequisite` 的非目标曾写"不新增任何……图片证据"。文祥 2026-09-24 明确接受修订——影像记录由 `2026-09-24-close-training-material-loop` 建立的**培训资料**能力承载，本 Change 只把资料接进档案事实，**不重新引入现场证据采集**。
- **不改**：功能项 44 原文一字不改（甲方要求）。规格「系统 MUST NOT 要求签到、出勤、扫码、定位或现场证据」条款**保留不变**；矛盾以"签到情况 = 线下成绩已录入"的映射消解，规格 FR-LRN-009 遗留的"签到方式和有效条件待确认"因此**不再需要甲方补充定义**——签到不再是独立采集项。
- 企业档案"可通过企业名称搜索查询"按**当前租户内机构名称匹配**理解（本条已人工确认，不再跟踪）。

## 目标与边界

1. **一次查询返回全部档案事实**：一期、企业、个人三视角共用同一份 `ArchiveViewVO`，覆盖计划、企业、培训内容、参训人员、签到情况、学员成绩、综合评价、奖惩、影像记录、附件、证书、数据统计。
2. **归档快照写实**：`reward_penalty_snapshot`、`certificate_snapshot` 写真实事实；影像与附件写入 `sts_archive_asset` 并保留来源附件关联。
3. **档案文件为 PDF 正本**：一期与个人档案输出 `application/pdf`，持久化受控 `fileInfoId`，下载回读同一文件。
4. **前端补全展示与操作**：一期档案详情（成绩表、签到情况、奖惩、影像/附件清单、统计）、个人档案详情页 + 证书入口、企业档案筛选与每期档案下载。
5. 边界：**不新增业务表、不做数据库迁移、不新增菜单、不引入影像转码或媒体播放器、不做 ZIP 档案袋、不改证书签发规则、不重开签到采集**。档案文件格式与内容生成**不新增第三方依赖**。

## 实施顺序

- Task 1：档案事实组装与契约扩展（后端事实 + `archive.openapi.json`）。
- Task 2：归档快照写实与资料资产接线。
- Task 3：档案文件 PDF 正本（一期 + 个人）。
- Task 4：PC 档案页展示与操作补全。
- Task 5：纵向验收、Review、QA、Retro 与状态同步。

Task 3 依赖 Task 1 的事实结构；Task 4 依赖 Task 1～3 的契约与文件端点。Task 5 的闭环判定以真实环境操作证据为准。
