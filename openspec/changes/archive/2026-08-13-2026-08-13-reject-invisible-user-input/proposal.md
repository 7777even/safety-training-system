# Proposal：拒绝用户资料中的不可见 Unicode 字符

## 背景

系统用户创建和维护接口目前主要使用 `@NotBlank`、`@Email` 等基础约束，无法阻止用户名、用户编码等字段混入零宽空格
（如 `U+200B`）或其他 Unicode 控制/格式字符。这些字符肉眼难以识别，却会参与唯一性比较、登录凭证拼装、查询和展示，可能造成看似相同的账号实际不同、无法登录或审计信息难以辨认。

密码字段的 API Contract 已规定调用方提交 64 位小写十六进制 SHA-256 摘要，但后端 DTO 当前只校验非空，也需要同步落实既有契约。

## 目标

1. 用户创建、用户更新和密码重置时，拒绝文本字段中的不可见 Unicode 控制、格式及异常分隔字符。
2. 明确覆盖零宽空格、零宽连接符、零宽非连接符、词连接符、BOM 和双向文本控制符等不可见字符。
3. 密码创建与重置严格校验为既有契约规定的 64 位小写十六进制 SHA-256 摘要。
4. 非法请求统一在 Controller 参数校验阶段返回 HTTP 400、业务码 1001，不进入 Service 或产生落库副作用。
5. 同步 `docs/api/system-admin.openapi.json` 的校验说明和示例。

## 用户价值

- 管理员无法误创建肉眼相同但实际编码不同的账号。
- 用户编码、姓名及资料展示保持可辨认，登录、查询与审计使用一致文本。
- 密码摘要输入与已发布 API Contract 保持一致，异常字符不会进入凭证存储。

## 功能范围

- 为后端提供可复用的 Jakarta Validation 不可见字符约束。
- 校验 `UserCreateRequest` 的全部可写字符串字段。
- 校验 `UserUpdateRequest` 的全部可写字符串字段。
- 校验 `ResetPasswordRequest.password`。
- 密码字段增加 64 位小写十六进制格式约束。
- 更新系统用户 OpenAPI 契约及 Controller Web Slice/standalone 参数校验测试。

## 非目标范围

- 仅后端；前端以 OpenAPI 为准另开，不包含页面、Mock、联调或 UI 验收。
- 不修改登录时的凭证标准化规则，不自动清洗、删除或替换输入字符。
- 不修改数据库结构、索引或历史用户数据，不创建 migration。
- 不批量清理既有账号；发现历史脏数据时另开数据治理 Change。
- 不禁止普通可见字符或普通半角空格，不新增用户名字符集、长度或大小写业务规则。
