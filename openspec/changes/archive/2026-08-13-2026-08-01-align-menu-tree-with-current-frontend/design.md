# Design：当前前端菜单树对齐方案

## 真相源与转换原则

1. `current-online-menu-tree.json` 决定 D/M/C 展示节点的名称、层级、路径、组件、图标和顺序。
2. Controller 的 `@SaCheckPermission` 决定必须存在的 F 权限集合；前端文件不完整的权限不得删除。
3. 输出仍为 `menus.json` 所需的扁平结构，不修改初始化程序的数据格式。
4. 根节点 `moduleId` 等于自身 ID；所有后代沿用所属根节点 `moduleId`。

## 稳定 ID 映射

- 优先按唯一组件路径匹配既有 D/M/C 节点并复用 ID。
- 组件为空时，按规范化完整路由路径及菜单类型匹配并复用 ID。
- F 节点按权限字符串匹配并复用既有 ID。
- 无法唯一匹配的新展示节点使用未占用的新固定 ID；不得按数组位置生成不稳定 ID。
- 不再出现在展示树中的旧 D/M/C 节点由 migration 删除；其仍有效的 F 权限先重新挂载，不随父节点删除。

## 权限归属

- 前端树已有同名权限时，F 节点挂到声明该权限的 C 节点。
- 其余后端权限按业务前缀挂到最接近的业务 C 节点；没有对应 C 节点时挂到所属业务 M/D 节点。
- 页面自身权限允许与其查询 F 节点复用；除此之外不新增重复权限。
- 转换后权限集合必须与 Controller 授权点完全一致。

## 存量数据库迁移

正式 migration 必须在事务内：

1. 更新复用 ID 的父节点、模块、名称、路径、组件、图标、排序和类型。
2. 幂等插入新增节点并为默认 `admin` 建立角色菜单关系。
3. 删除废弃节点前先处理角色菜单关系，并确认其有效 F 权限已迁移。
4. 自定义角色对复用权限 ID 的授权保持不变；新增展示节点不自动扩大自定义角色权限。
5. 不修改表、字段、索引及 `superAdmin` 特权旁路。

## 验证

- 先扩展测试表达前端树转换、稳定 ID、父子关系和权限全集要求，并观察旧菜单失败。
- 验证 `menus.json` ID 唯一、父节点存在、根模块正确、权限与 Controller 完全一致。
- 使用 MySQL IT 验证 migration 后菜单树及角色关系；Docker 不可用时如实报告。

## 风险与取舍

- 同一路径片段可出现在不同父节点下，因此匹配使用完整路径而非单个 `path`。
- 前端文件缺少 85 个后端权限；选择保留并重新归属，避免普通角色失去真实后端能力。
- 菜单重排会改变已有角色可见目录，但复用 F 权限 ID 可最大限度保持原授权。
