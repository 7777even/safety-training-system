# Proposal：所有 PDF 预览文件线性化

## 背景

当前文档预览统一使用 PDF.js，并由受控文件代理提供 HTTP Range。Office 文档经 OnlyOffice 生成 PDF，原生 PDF 则直接使用源文件。现有设计仅把
`qpdf --linearize` 记录为二期方向，实际产物没有统一保证 Fast Web View，较大文件首屏可能仍需读取较多尾部交叉引用数据。

## 目标

1. 所有进入在线预览链的 PDF 均无条件执行 `qpdf --linearize`，不设置文件大小阈值。
2. Office 转换 PDF 与原生上传 PDF 使用同一线性化、校验、失败和清理规则。
3. 线性化预览继续通过既有受控文件代理和 HTTP Range 交付，不暴露对象存储地址。
4. 部署环境显式检查 qpdf，不允许配置缺失时静默产生未线性化的新预览文件。

## 用户价值

- PDF.js 可结合 Range 更早获得首屏所需结构，改善大 PDF 首次打开体验。
- 新上传 PDF 预览载体保持一致，避免原生 PDF 与 Office 派生 PDF 行为分叉。
- 原文件保持不变，下载、审计和失败恢复不受预览优化影响。

## 功能范围

- 新上传原生 PDF 改为异步创建 `DOCUMENT_PREVIEW` 任务，不再直接以源文件标记处理成功。
- Office 文档经 OnlyOffice 转为 PDF 后，再执行 qpdf 线性化和完整性校验。
- 原生 PDF 从私有存储读取后执行 qpdf 线性化和完整性校验。
- 线性化结果作为 `PREVIEW` 派生文件登记，回写真实 `pageCount`。
- qpdf 路径和执行超时纳入部署配置。
- 同步后端部署文档、OpenAPI 中原生 PDF 的处理状态语义、自动化测试和工程记录。

## 非目标范围

- 不新增前端页面、Mock 或联调任务；前端以 OpenAPI 为准另开。
- 不新增按页图片、按页 PDF 或服务端页面渲染接口。
- 不改变 PDF.js、play-info URL、Range HTTP 契约、权限模型或对象存储边界。
- 不承诺在任意网络和终端上瞬时打开；本能力优化首屏与渐进读取，不改变文件实际传输成本。
- 不修改数据库结构，不引入 Java 生产依赖。
- 不扫描、回补或替换历史 PDF；既有素材保持原状。

## 人工确认

- 2026-08-13：已确认所有 PDF 无条件线性化，不区分大小；前端继续使用现有 PDF.js 与 Range；允许安装 qpdf 并继续实施。
- 2026-08-13：确认本 Change 只处理新创建素材，不需要历史 PDF 回补。
