# 设计：优化考试成绩处置与补考资格展示

## 总体方案

成绩处置页继续读取既有“作答详情”和“成绩发布流水”。前端使用作答详情中的题目快照、答案、自动分、人工分和最终分渲染只读核对区，不新增成绩计算逻辑。

补考资格由作答详情新增的 `retakeEligibility` 返回。服务端将开补考前的策略验证提炼为同一只读判定，开补考写操作仍须再次执行该验证，避免读取后策略、时间或作答事实变化造成越权创建。

## 成绩处置页面

页面自上而下分为：

1. **考生与本次作答概览**：考生姓名/工号（已有时）、作答状态、交卷时间、成绩发布状态、总分、及格结果和待批阅题数。未发布但已完成批阅时，及格结果由服务端返回
   `predictedIsPassed`；待阅时为空。
2. **逐题核对**：按作答题序展示题干、题型、考生答案、自动得分、人工得分、最终得分及批阅状态；客观题与主观题均只读，长答案自然换行。未完成批阅的主观题须明确标识。
3. **成绩操作**：未发布且不存在待批阅主观题时允许发布；存在待批阅题时仅展示阻断说明；已发布时显示只读发布结果。
4. **补考资格**：展示策略摘要和逐项判定。仅当全部项目通过且用户具备 `exam:attempt:start` 权限时显示“开补考”；不通过时保留原因说明但不渲染操作按钮。
5. **成绩发布流水**：保留现有追加型发布记录。

## 补考资格判定

新增作答详情字段：

```text
retakeEligibility:
  eligible: boolean
  reasons: string[]
  usedRetakeCount: number
  maxRetakeCount: number
```

`eligible=true` 的必要条件：

1. 考试补考开关 `isRetakeEnabled=1`。
2. 考生状态符合 `retakeScope`：FAILED 须正式成绩已发布且不及格；ABSENT 为缺考；FAILED_OR_ABSENT 两者均可。
3. 当前时间处于 `retakeStartTime`、`retakeEndTime` 的闭区间；未设置的一端不限制。
4. 当前考生非作废 `RETAKE` 尝试数小于 `retakeMaxCount`。
5. 考试状态允许补考（PUBLISHED、RUNNING、ENDED）。
6. 当前考试存在可用于生成作答快照的冻结试卷/题库规则；补考复用该考试的既有冻结试卷和规则，不选择其他试卷。

`reasons` 返回面向教师的中文未满足原因，允许同次返回多个原因。前端不自行判定上述业务规则，仅展示服务端结果。权限不足不写入
`eligible` 业务判定，由页面独立控制操作可见性。

## API Contract

更新 `GET /api/exam/attempts/{examAttemptId}` 的 `ExamAttemptVO`：增加可空 `retakeEligibility`
对象。它是只读提示信息，不改变既有开补考接口的请求或响应。

`POST /api/exam/candidates/{examCandidateId}/retake` 保持原 Contract
和业务错误码，并在执行创建前重用相同的资格校验。若冻结试卷/规则不可用，返回既有统一业务错误外壳中的明确错误码与中文提示（具体码在实现时以现有考试错误码段补充
OpenAPI）。

## 数据、权限与兼容性

- 不新增表、不做 migration，不改变考生成绩、发布流水或作答快照。
- 补考资格读取沿用作答详情的数据范围权限；创建仍要求 `exam:attempt:start`。
- 旧客户端可忽略新增字段；新页面将字段缺失视为“不显示开补考并提示无法取得资格判定”，不能退回到仅检查开关的旧行为。

## 风险与取舍

- 资格必须由服务端计算，否则前端无法可靠判断跨多次作答的已用补考次数。取舍是扩展一次只读响应，而不是新增独立查询接口，降低页面加载往返。
- 时间窗口在读取和点击间可能变化，因此写接口必须再次校验；前端资格仅用于展示和减少无效点击。
- 冻结试卷有效性必须复用开始作答所需前置检查，不能只检查 `paperVersionId` 非空而忽略题目快照生成失败风险。
