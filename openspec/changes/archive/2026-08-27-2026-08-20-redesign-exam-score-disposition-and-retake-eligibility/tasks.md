## Task 1：提供作答维度的补考资格判定

状态：已完成（2026-08-20）

- Owner：Codex
- 输入：考试策略、考生状态、作答记录、冻结试卷/题库规则和现有开补考服务。
- 输出：作答详情返回补考资格、未满足原因及已用/最大补考次数；开补考写操作复用同一规则并继续二次校验。
- 前后端影响：后端增加只读响应字段；前端以 OpenAPI 为准接入。
- API 依赖：更新 `GET /api/exam/attempts/{examAttemptId}` 的 `ExamAttemptVO`；保持开补考请求 Contract 不变。
- 数据影响：无 schema 或 migration；仅读取现有考试、考生、作答及题目快照事实。
- 验收标准：启用、范围、窗口、次数、考试状态和冻结试卷规则全部满足时 `eligible=true`；任一不满足时为 false
  且含中文原因；创建补考仍在写入前执行同一验证。
- 测试方式：先补零 DB 服务测试覆盖各条件与无写入护栏；更新 OpenAPI 示例和契约断言。

## Task 2：重构成绩处置页为发布前核对视图

状态：已完成（2026-08-20）

- Owner：Codex
- 输入：作答详情题目快照、答案/得分/批阅状态、发布流水和 Task 1 的补考资格字段。
- 输出：PC 成绩处置页展示考生概览、逐题答案与得分、待批阅提示、发布操作、补考资格说明及流水。
- 前后端影响：仅 PC 管理端消费既有作答数据和新增资格字段；不新增 Mock 或生产依赖。
- API 依赖：`GET /api/exam/attempts/{examAttemptId}`、成绩发布与开补考既有接口。
- 数据影响：无。
- 验收标准：教师能看到每题答案、自动分/人工分/最终分和批阅状态；有待批阅题时不能发布；全部补考资格通过且有权限才显示“开补考”，否则显示具体原因且无按钮。
- 测试方式：先写可执行前端状态/渲染数据测试，覆盖发布阻断、逐题得分映射和资格显示；运行目标测试、typecheck 与 lint。
