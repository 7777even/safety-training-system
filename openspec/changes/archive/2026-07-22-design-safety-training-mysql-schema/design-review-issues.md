## 4. 问题二：角色组织管理范围缺失（已确认）

### 4.1 产品要求

FR-ENT-SYS-003 要求管理员创建子角色时，同时分配：

- 功能权限，例如课程查看、课程编辑、考试管理、成绩导出。
- 组织管理范围，例如只能管理某学院、某部门、某班级及其下级节点。

产品核心规则还要求角色只能访问被授予的功能和组织范围内的数据。

### 4.2 决策记录

| 项目     | 结论                                                                            |
|--------|-------------------------------------------------------------------------------|
| 决策状态   | 已确认                                                                           |
| 确认日期   | 2026-07-21                                                                    |
| 确认方    | 需求方                                                                           |
| 组织树    | 复用并扩展 `us_sys_dept`                                                           |
| 角色     | 复用并扩展 `us_sys_role`                                                           |
| 用户角色   | 复用 `us_sys_user_role`                                                         |
| 功能权限   | 复用 `us_sys_role_menu` 和 `us_sys_menu.perms`                                   |
| 数据权限   | 新增 `us_sys_role.data_scope` 与 `us_sys_role_dept`                              |
| 删除的重复表 | `sts_org_unit`、`sts_org_role`、`sts_org_member_role`、`sts_org_role_permission` |

### 4.3 原问题本质

功能权限回答“能不能操作”，组织范围回答“能操作哪些人的数据”。只有功能权限而没有组织范围，会出现以下情况：

```text
角色：A 学院培训管理员
功能权限：查看课程学习详情、导出考试成绩
预期数据范围：A 学院及其下属班级
当前模型结果：只能限制在整个机构，无法限制到 A 学院
```

如果应用默认按机构查询，该管理员可能看到 B 学院的学员、考试和培训数据；如果应用临时在各模块写特殊条件，又会形成不一致的权限实现。

### 4.4 统一后的表职责

| 表                  | 职责        | 本次变化                                                                      |
|--------------------|-----------|---------------------------------------------------------------------------|
| `us_sys_dept`      | 机构内无限级部门树 | 增加 `organization_id`、`dept_code`、`dept_type`、`description` 及机构组合索引        |
| `us_sys_role`      | 机构角色及数据范围 | 增加 `organization_id`、`role_level`、`is_builtin`、`data_scope`、`description` |
| `us_sys_user_role` | 用户与角色关系   | 继续复用，绑定时强制校验用户部门与角色属于同一机构                                                 |
| `us_sys_menu`      | 菜单和功能权限点  | 培训权限统一保存于 `perms`                                                         |
| `us_sys_role_menu` | 角色与功能权限关系 | 继续复用，只负责功能权限                                                              |
| `us_sys_role_dept` | 自定义部门数据范围 | 新增；保存角色、部门和是否包含下级                                                         |

### 4.5 数据范围语义

| 范围                  | 语义                                          |
|---------------------|---------------------------------------------|
| `ALL`               | 平台全部机构数据，仅限经确认的平台级特权角色                      |
| `ORGANIZATION`      | 当前角色所属机构全部数据                                |
| `DEPT`              | 当前用户主部门数据                                   |
| `DEPT_AND_CHILDREN` | 当前用户主部门及所有下级部门数据                            |
| `CUSTOM`            | `us_sys_role_dept` 指定的一个或多个部门；每条可单独决定是否包含下级 |
| `SELF`              | 当前用户本人创建、负责、被分配或作为数据主体的数据                   |

本期不设计按字段条件、标签表达式、SQL 或任意脚本的数据权限。

### 4.6 需要区分的权限概念

| 权限概念    | 示例             | 当前模型          |
|---------|----------------|---------------|
| 功能权限    | 可以编辑课程         | 已支持           |
| 机构隔离    | 只能访问当前企业       | 已支持           |
| 组织范围    | 只能访问 A 学院及下级班级 | 本次已补充         |
| 任务归属    | 老师只能处理被分配的考试   | 已有业务关系，需服务层校验 |
| 资源级管理权限 | 某管理员可维护指定课程    | 已有通用资源权限      |
| 跨机构授权   | 企业可使用平台公共课程    | 已有机构资源授权      |

这些权限不能互相替代。

### 4.7 服务端执行规则

权限计算顺序为：

```text
登录账号有效
→ 当前机构成员有效
→ 系统角色具有菜单/按钮功能权限
→ 角色 data_scope 包含目标人员/业务对象
→ 满足老师任务归属、学员本人或资源级授权
```

数据范围必须应用于列表、详情、统计、导出、批量操作和异步任务。人员与执行事实按数据主体用户的部门过滤；课程、题库、试卷等管理资源按创建人部门过滤，并叠加显式资源管理员授权。统计必须先过滤基础事实再聚合。

角色、部门、用户部门和角色菜单变化后必须清理权限缓存。部门移动按当前树动态改变后续访问范围，已发布参与名单和归档快照不改写。

### 4.8 权限规则确认结果

- [x] 一个用户具有多个角色时，数据范围取并集；只有授予当前功能权限的角色参与本次范围合并。
- [x] 账号有效且 `user_code` 大小写敏感地严格等于 `superAdmin` 时，硬编码绕过功能权限、机构边界和部门数据范围。
- [x] 其他用户不按角色编码、名称或级别享受隐含特权，严格按角色自己的功能权限和 `data_scope` 执行；配置为 `ALL` 时按 `ALL`
  范围执行。
- [x] 一个普通账号只属于一个主要机构和主部门，不支持在多个机构分别任职或切换机构角色；`superAdmin`、监管关系和跨机构资源授权按独立机制处理。

### 4.9 验收标准

- [x] 设计中删除四张重复培训组织/RBAC 表并明确系统表映射。
- [x] DDL 草案增加六类数据范围和 `us_sys_role_dept`。
- [ ] A 学院管理员无法查询、导出或统计 B 学院数据。
- [ ] 同一权限规则应用于列表、详情、统计、导出和异步任务。
- [ ] 不通过前端隐藏按钮代替后端数据权限。
- [ ] 权限测试覆盖越权 ID、跨组织导出、统计聚合、角色变更、部门移动和成员调岗。

## 5. 问题三：课程内考试/练习执行关联不明确（已确认）

### 5.1 产品要求

课程章节可以编排理论题库、测验、专项练习和考试。系统需要按章节记录：

- 学员是否参加。
- 每题答案、正确率和错题。
- 作答次数和最终成绩。
- 该成绩属于哪门课程、哪次开课和哪个章节内容项。

### 5.2 调整前设计

调整前的课程链路为：

```text
课程定义
→ 课程章节
→ 课程内容项 course_item（保存 exam_id）
→ 课程开课 course_offering
→ 课程报名 course_enrollment
→ 内容项进度 course_item_progress（只保存次数、最佳分等汇总）
```

调整前的考试侧链路为：

```text
考试 exam
→ 考试人员 exam_candidate
→ 作答尝试 exam_attempt
→ 答案与批阅
```

`exam_candidate` 只有：

- `assignment_source=COURSE`
- 泛化的 `source_business_id`
- `(exam_id, user_id, deleted)` 唯一键

没有明确的 `course_item_id`、`course_offering_id` 或 `course_enrollment_id`。

### 5.3 原问题本质

同一个考试可能被：

- 直接分配给学员。
- 编排到两门不同课程。
- 编排到同一课程的两个内容项。
- 由同一课程多次开课使用。
- 同时用于培训计划和独立考试。

当前 `(exam_id,user_id)` 唯一键只允许同一用户在同一考试下存在一条有效候选记录。若同一考试在多个课程上下文中复用，系统无法区分成绩属于哪次开课和哪个章节。

仅依赖 `assignment_source + source_business_id` 也存在以下问题：

- `source_business_id` 的目标表不直观，无法依靠数据库字段语义确认。
- 无法同时表达课程内容项、开课和报名三个层级。
- 课程学习报告只能根据用户和考试反查，容易把其他场景的成绩算入本课程。
- 清除练习记录或课程重学时，可能影响同一考试的其他业务来源。

### 5.4 决策记录

| 项目   | 结论                                                                                 |
|------|------------------------------------------------------------------------------------|
| 决策状态 | 已确认                                                                                |
| 确认日期 | 2026-07-21                                                                         |
| 确认方  | 需求方                                                                                |
| 设计原则 | 简单直接关联，不增加测评任务、课程专用考试或课程专用答卷模型                                                     |
| 内容编排 | `course_item.item_type=EXAM/PRACTICE` 时直接关联 `exam_id`                              |
| 执行来源 | `exam_candidate` 直接保存 `course_offering_id`、`course_item_id`、`course_enrollment_id` |
| 作答成绩 | 继续复用 `exam_attempt`、答案、批阅和成绩发布表                                                    |

### 5.5 简单执行规则

课程结果链固定为：

```text
课程报名
→ 课程内容项
→ 考试人员
→ 考试尝试
→ 成绩
```

1. 课程内容项直接引用现有考试或练习，同一个考试允许被不同课程内容项和开课复用。
2. 学员首次从课程内容项进入时，按“课程报名 + 内容项”幂等创建考试人员记录。
3. `assignment_source=COURSE` 时，三个课程来源 ID 必须同时存在，且 `source_business_id=course_item_progress_id`，用一个 ID
   唯一标识“报名 + 内容项”执行上下文。
4. 同一学员在不同开课或不同内容项中使用同一考试时，分别生成考试人员记录，尝试和成绩互不覆盖。
5. 补考、课程重学或练习重置只处理当前考试人员及其尝试，不影响同一考试的其他来源记录。
6. 课程内容项进度读取当前考试人员的 `attempt_count`、`best_score`、`final_score` 和最终状态；课程报告不读取独立考试或培训直接下发的成绩。
7. 培训计划通过课程产生的成绩沿课程报名链路归集；培训直接下发的考试使用 `TRAINING` 来源，两者不共享考试人员记录。

### 5.6 本期不做

- 不拆分“考试模板”和“考试执行场次”。
- 不新增统一测评任务聚合。
- 不新增课程专用答卷、答案或成绩表。
- 不设计跨来源成绩共享和复杂成绩选择策略。

### 5.7 验收标准

- [x] DDL 草案中的考试人员已补充开课、内容项和报名 ID，并调整上下文唯一键。
- [x] OpenSpec 已明确课程考试/练习复用统一考试作答和成绩链。
- [ ] 同一用户在两个开课中参加同一测评时，生成两组互不覆盖的执行记录。
- [ ] 任一考试尝试都能直接追溯到课程内容项和课程报名。
- [ ] 课程报告、错题和章节进度只统计当前课程执行上下文内的数据。
- [ ] 培训直接下发考试和课程内考试的来源记录互不混用。

## 6. 问题四：课程和问卷发布后的版本策略（已确认）

### 6.1 为什么需要版本或快照

发布前的内容允许反复编辑；发布后已经产生学习、作答或统计事实。若仍直接修改原内容，会出现“历史记录引用的是同一个 ID，但该 ID
的业务含义已经改变”的问题。

### 6.2 课程调整前风险

调整前课程、章节、内容项均为可就地修改的 A 类表；开课只关联 `course_id`，学习进度关联可变的 `course_item_id`。

可能发生：

1. 学员完成了视频 A，管理员后来把同一内容项替换为视频 B。
2. 学员完成了考试项，管理员后来更换该项关联的考试。
3. 已结束开课查询课程报告时，展示的是修改后的目录和标题。
4. 删除或移动章节后，历史学习进度无法按原目录重放。

调整前设计只使用“参与后锁定内容项”等服务规则降低风险，未明确课程整体如何发布、修改和生成新版本。

### 6.3 问卷调整前风险

调整前问卷、题目、选项和子项均为可修改 A 类表；答卷直接关联这些可变 ID，没有问卷版本或题目文本快照。

可能发生：

1. 用户回答“是否满意”，管理员后来把题目改为“是否不满意”。
2. 选项 A 原来表示“满意”，后来改为“不满意”，历史统计含义反转。
3. 问卷发布后增加、删除或排序题目，已提交答卷和未提交草稿结构不一致。

仅靠“发布后禁止修改”可以避免污染，但必须与产品要求中的“编辑、复制、删除”行为明确区分。

### 6.5 统一版本规则

1. 草稿状态下，课程章节/内容项和问卷题目/选项/子项可以在结构化表中直接编辑。
2. 每次正式发布在事务内生成递增 `version_no`、完整 `content_snapshot_json`、`snapshot_hash`、发布人和发布时间，再更新主表
   `current_version_id`。
3. 发布版本为 C 类不可变记录，不允许更新或删除；重复的同一发布请求必须幂等，不重复生成版本。
4. 已发布内容需要修改时继续编辑工作草稿，再次发布形成下一版本，不覆盖旧版本。
5. 新开课只绑定发布时的当前课程版本，发布后不得自动升级；已有开课和学习事实始终读取原版本。
6. 新一轮问卷发布按当前问卷版本生成参与人；已经开始的答卷草稿和已提交答卷始终读取其原 `survey_version_id`。
7. 课程下线、问卷关闭或撤回只改变业务状态，不删除发布版本；历史报告按绑定版本展示。
8. 问卷统计默认按版本统计；需要跨版本汇总时必须明确展示版本范围，不能把题目含义不同的版本直接混算。

## 7. 问题五：考试结果通知接收人和综合成绩聚合规则（已确认）

### 7.1 子问题 A：考试结果通知接收人（已确认）

#### 决策记录

| 项目      | 结论                      |
|---------|-------------------------|
| 决策状态    | 已确认                     |
| 确认日期    | 2026-07-21              |
| 确认方     | 需求方                     |
| 接收人确定方式 | 考试管理员直接选择一个或多个通知用户      |
| 负责人关系   | 不建设部门负责人、成员直属上级或岗位负责人关系 |
| 未选择接收人  | 不推送考试结果                 |

#### 设计结论

- 不再保留“是否通知直属负责人”开关，也不根据部门、组织树、角色编码、角色名称或岗位名称推导接收人。
- 每场考试通过 `sts_exam_policy.result_notify_audience_id` 绑定结果通知范围；字段为 `NULL` 时表示不推送。
- 通知范围使用 `sts_common_audience`，固定为 `purpose=NOTIFICATION`、`resolve_mode=FROZEN`。
- 考试结果通知只接受管理员直接选择的用户，范围规则使用 `subject_type=USER`，最终用户快照保存到
  `sts_common_audience_member`。
- 成绩发布后，为已选且当时有效的用户生成 `sts_common_message_recipient`；每位用户的发送成功、失败和已读状态分别记录。
- 历史通知接收人以冻结快照和消息接收人记录为准，用户后续调岗、角色变化或部门变化不重算历史接收人。

#### 处理示例

```text
管理员配置考试
→ 直接选择用户 A、用户 B 作为结果通知人
→ 发布考试时冻结通知用户快照
→ 考试成绩发布
→ 仅向用户 A、用户 B 生成消息接收记录
```

该方案满足调研中“考试结束后推送结果”的业务目的，同时不引入当前没有明确需求的汇报线或负责人数据模型。

### 7.2 子问题 B：综合成绩聚合规则（已确认）

#### 决策记录

| 项目   | 结论                                                     |
|------|--------------------------------------------------------|
| 决策状态 | 已确认                                                    |
| 确认日期 | 2026-07-21                                             |
| 确认方  | 需求方                                                    |
| 方案   | 为每个计分课程/考试计划内容单独配置权重，同类型结果按计划配置聚合                      |
| 聚合方式 | 本期只支持 `AVERAGE`、`WEIGHTED_AVERAGE`                     |
| 补考来源 | 使用考试策略已经确定的 `exam_candidate.final_score`，综合成绩服务不重新选择尝试 |
| 复杂能力 | 不增加成绩贡献明细表，不实现公式引擎、否决、封顶或保底                            |

#### 数据设计

`sts_training_plan_content` 增加：

- `is_scored`：是否计入综合成绩，本期只允许课程和考试内容启用。
- `score_weight`：同类型内容聚合权重。
- `score_aggregation_mode`：同类型聚合方式，取 `AVERAGE` 或 `WEIGHTED_AVERAGE`。

课程报名增加 `final_score`，作为课程内容的正式成绩来源；考试内容继续读取考试人员的正式 `final_score`
。进入聚合前统一换算为百分制，考试按正式得分除以对应试卷总分换算，换算过程写入计算来源快照。

#### 计算规则

1. 同一培训计划允许配置多个计分课程和多个计分考试。
2. 同一类型的计分内容必须使用相同聚合方式。
3. `AVERAGE` 采用等权平均；`WEIGHTED_AVERAGE` 要求每项权重大于 0，且同类型权重合计为 1。
4. 课程成绩读取对应课程报名的正式成绩；考试成绩读取对应考试人员的正式最终成绩，补考最高分或最后一次成绩由考试策略先行确定。
5. 任一必需计分内容尚未产生正式成绩时，综合成绩保持未计算或不完整，不自动按 0 分处理。
6. 先聚合得到 `course_score`、`exam_score`，再按已绑定综合评价表单版本中的来源类型权重计算 `composite_score`
   ，最后应用奖惩或人工基础加减分。
7. 培训计划发布后锁定计分内容、权重和聚合方式；计算快照保存计划内容、课程报名/考试人员、原始分、百分制分、权重、聚合方式、中间结果和规则版本。

#### 示例

```text
课程 A：80，权重 40%
课程 B：90，权重 60%
课程聚合方式：WEIGHTED_AVERAGE
course_score = 80 × 40% + 90 × 60% = 86

考试 A 正式最终成绩：75，权重 50%
考试 B 正式最终成绩：85，权重 50%
考试聚合方式：WEIGHTED_AVERAGE
exam_score = 75 × 50% + 85 × 50% = 80
```

本期线下成绩继续作为已经确认的 `offline_score` 来源类型分参与第二层权重计算；多线下成绩的复杂聚合不在本次课程/考试内容规则中扩展。

### 8.2 可空唯一键修复

以下字段原先使用 `NULL` 表示“不限”或“非选项”，会使 MySQL 唯一键允许语义重复，现统一改为非空哨兵值：

| 表和字段                                     | 修复后规则                                                         | 唯一性效果                     |
|------------------------------------------|---------------------------------------------------------------|---------------------------|
| `sts_common_audience_rule.subject_id`    | `NOT NULL DEFAULT 0`；`subject_type=ALL` 固定使用 `0`，其他类型必须为正数 ID | 同一范围不能重复配置相同的 ALL 或具体对象规则 |
| `sts_question_asset.option_key`          | `NOT NULL DEFAULT ''`；STEM/ANALYSIS 使用空字符串，OPTION 必须填写选项键     | 非选项素材和选项素材都能被唯一键稳定去重      |
| `sts_paper_draw_rule.difficulty`         | `NOT NULL DEFAULT 'ALL'`                                      | “不限难度”的抽题规则不能重复           |
| `sts_paper_draw_rule.knowledge_point_id` | `NOT NULL DEFAULT 0`                                          | “不限知识点”的抽题规则不能重复          |

以下 `NULL` 属于业务允许的“尚未分配”或“该类型不适用”，不应强制只能存在一条，因此保留条件唯一语义：

- `sts_org_member.employee_no`：未分配工号的成员允许多条；填写工号后在机构内唯一。
- `sts_common_audience.business_type/business_id`：TEMPLATE 范围允许多条空业务对象；BOUND 范围必须同时填写，并按业务对象和用途唯一。
- `sts_exam_candidate.course_enrollment_id/course_item_id`：只有 `assignment_source=COURSE` 时必须同时填写并唯一；其他来源允许为空。
