- 4 项 P0 结构问题已在 OpenSpec 和 DDL 草案中修复。
- 5 项 P1 高风险问题已在 OpenSpec 和 DDL 草案中修复。

## 4. 阻断级问题（P0）

以下保留首次评审时的证据、影响和建议，当前修复状态以 2.1 节为准。

### P0-01 考试人员业务身份与唯一键不一致（已修复）

#### 需求与设计目标

正式考试需要按班级、人员范围或导入名单分配参考人员。同一个独立考试中的同一用户应只有一条有效考试人员记录；同一考试被多个课程开课或培训上下文复用时，又必须允许按执行上下文隔离考试人员。

`design.md` 的关键关系也声明：“一个考试同一用户最多一条有效人员记录”。

#### 修复前设计

`sts_exam_candidate` 使用以下唯一键：

```sql
UNIQUE KEY uk_exam_user_context_deleted
  (exam_id, user_id, assignment_source, source_business_id, deleted)
```

`assignment_source` 包含 `AUDIENCE/IMPORT/LINK/COURSE/TRAINING`。

#### 问题

`assignment_source` 是人员进入考试的渠道，不应成为考试人员业务身份的一部分。同一独立考试中的同一用户先被参与范围解析，再被名单导入或通过链接加入时，可以产生多条有效考试人员记录。

可能造成：

- 应考人数、参考人数和缺考人数重复。
- 多条作答链、尝试次数和最终成绩相互分裂。
- 成绩发布、积分、证书和通知重复触发。
- 无法确定哪条考试人员记录是正式结果。

#### 已采用方案

引入明确执行上下文：

```text
context_type：STANDALONE / COURSE / TRAINING
context_id：
  STANDALONE 固定为 0
  COURSE 使用 course_item_progress_id
  TRAINING 使用 plan_content_id，并另存 training_participant_id
```

唯一键调整为：

```text
exam_id + user_id + context_type + context_id + deleted
```

`assignment_source` 仅保存分配来源，不参与考试人员身份唯一性。

#### 验收标准

- 同一独立考试中，同一用户通过范围、导入和链接重复加入时仍只有一条有效考试人员记录。
- 同一用户从两个课程开课参加同一考试时，生成两条互不覆盖的课程上下文记录。
- 应考统计、成绩发布、证书和消息均只读取唯一正式考试人员记录。

### P0-02 题库练习和线下考试无法与作答尝试闭环（已修复）

#### 修复前设计

- `sts_exam_exam` 允许 `BANK_PRACTICE` 只绑定 `question_bank_id`。
- `sts_exam_attempt.paper_version_id` 为 `NOT NULL`。
- 设计文字说明题库练习开始时“生成并冻结一次试卷快照”。
- 线下考试暂定只创建结果型尝试，不生成逐题答卷。

#### 问题

题库练习和线下考试可能没有现成 `paper_version_id`，但当前作答尝试不能在没有试卷版本的情况下创建。设计没有明确动态试卷是：

- 临时创建正式 `sts_paper_paper/sts_paper_version`；
- 创建独立的考试试卷实例；还是
- 仅依赖 `sts_exam_attempt_question` 快照。

如果为每次题库练习创建隐藏试卷主表和版本，将产生大量无业务身份的试卷记录；如果不创建，则违反非空约束。线下结果型尝试存在同样冲突。

#### 已采用方案

二选一并在 OpenSpec 中明确：

1. 增加不可变的 `exam_attempt_paper` 执行试卷实例；或
2. 允许 `paper_version_id` 为空，并在考试尝试上冻结总分、合格分、时长、题序、多选计分方式等执行级参数。

无论选择哪种方式，实际题目、选项、正确答案和分值仍由尝试题目快照保存。

#### 验收标准

- 题库练习无需预建正式试卷即可创建作答尝试并完整重放。
- 线下考试可以保存正式结果型尝试，不要求虚构试卷版本。
- 题库、题目或考试配置后续变化不影响既有练习结果。

### P0-03 问卷缺少发放批次和业务场次（已修复）

#### 需求

问卷可用于线下培训调查和学员对培训机构的评价；培训中可以发起问卷，结果和统计需要定位到对应培训或评价对象。

#### 修复前设计

- `sts_survey_target_binding` 可以把同一问卷绑定到课程、考试、培训或机构。
- `sts_survey_participant` 不保存 `survey_binding_id` 或其他发放场次 ID。
- 参与人唯一键为 `survey_version_id + user_id + deleted`。

#### 问题

同一问卷版本被两期培训复用时，同一学员只能生成一条参与记录：

- 第二期培训无法再次答卷。
- 已提交答卷无法定位到具体培训期次。
- 培训问卷统计、机构评价统计会相互串数据。
- 同一内容、不同参与范围或截止时间的多次发放无法表达。

#### 已采用方案

增加问卷发放实例，例如 `sts_survey_campaign` 或 `sts_survey_instance`，至少保存：

- `survey_version_id`
- `survey_binding_id` 或明确的 `source_type + source_id`
- `audience_id`
- 发布、开始和截止时间
- 发放状态
- 匿名、结果可见范围等本次发放规则快照

参与人唯一键改为：

```text
survey_instance_id + user_id + deleted
```

答卷通过参与人追溯到问卷发放实例。

#### 验收标准

- 同一学员可以在两期培训中分别提交同一问卷版本。
- 每份答卷能够唯一定位问卷版本、发放批次和业务对象。
- 统计可以分别按培训、课程、考试、机构和发放批次查询。

### P0-04 园区标准/模板跨机构引用与同机构校验规则冲突（已修复）

#### 需求

园区监管端维护培训类型和标准化培训计划模板，企业或培训机构可以引用模板建立实际培训计划。

#### 修复前设计

- `sts_training_type`、`sts_training_standard`、`sts_training_template` 均属于一个 `organization_id`。
- 企业培训计划直接保存 `training_type_id`、`training_standard_id`、`source_template_id`。
- 全局一致性规则要求被引用记录与当前业务对象属于同一机构。
- 跨机构资源授权目前只列出 `COURSE/QUESTION_BANK/PAPER/EXAM/TEMPLATE`，没有 `TRAINING_TYPE` 和 `TRAINING_STANDARD`。

#### 问题

园区拥有的培训类型、标准和模板被企业引用时，企业培训计划必然出现跨机构逻辑引用；这与全局“引用必须同机构”的规则冲突。

如果实施时直接复制类型、标准和模板，则必须定义编码、版本、来源快照和园区更新是否影响企业副本；当前设计也没有说明。如果直接跨机构引用，则必须补充授权和数据访问规则。

相同问题还会影响培训机构承办企业员工培训：参训人员有 `participant_org_id`
，但学习和考试事实通常属于培训计划或开课的主办机构，需要明确登录主体机构与业务数据所属机构是两个不同维度。

#### 已采用方案

由产品和架构负责人确认以下方案之一：

1. **复制冻结方案**：企业引用园区模板时，复制类型、标准和模板内容到计划快照，保留来源园区、来源版本和校验哈希，不再依赖园区当前记录。
2. **显式跨机构引用方案**：将培训类型、标准、模板加入跨机构授权模型，以监管关系和资源授权共同校验，并明确只读、使用、管理权限。

同时区分：

- `principal_organization_id`：当前登录用户主要所属机构。
- `owner_organization_id`：课程、考试或培训事实所属机构。
- `participant_organization_id`：参训人员所属机构。

学员本人任务访问应由报名、考试人员或参训人员事实授权，不能要求学员成为主办机构成员。

#### 验收标准

- 企业能够引用园区模板创建计划，且不会违反逻辑外键机构一致性规则。
- 园区模板后续修改不会无审计地改变已发布企业培训计划。
- 企业员工可以访问培训机构主办的本人培训、课程和考试，但不能访问主办机构其他数据。

## 5. 高风险问题（P1）

以下保留首次评审时的风险描述，当前修复状态以 2.1 节为准。

### P1-01 课程理论题库章节缺少逐题执行记录（已修复）

需求要求理论题库章节记录每题答题情况、正确率和错题。当前课程统一考试执行链只覆盖 `EXAM/PRACTICE`，`QUESTION_BANK`
内容项只有题库关系和汇总进度，没有对应考试人员、尝试和逐题答案上下文。

建议将课程理论题库章节统一实例化为 `BANK_PRACTICE` 执行对象，或者取消可独立执行的 `QUESTION_BANK` 类型，统一映射为
`PRACTICE + exam_id`。

验收时应确认每次课程题库练习都能追溯到课程报名、内容项、考试人员、尝试、题目和答案。

### P1-02 练习重置缺少考试人员上下文（已修复）

`sts_exam_practice_reset` 只有 `exam_id + user_id + reset_time`，没有 `exam_candidate_id`、课程报名或培训上下文。

同一考试复用于多个开课或培训时，一个上下文执行“清除练习记录”，可能同时隐藏其他课程、培训或独立练习事实，与课程考试上下文隔离决策冲突。

建议至少增加 `exam_candidate_id`，重置水位按考试人员执行链生效；收藏等确需用户全局共享的数据另行定义，不与练习重置混用。

### P1-03 考试人员历史快照不完整（已修复）

原始调研明确要求“指定考试人员”支持历史快照。当前冻结参与范围只保存用户 ID、决策和解析时间，考试人员也未冻结账号、姓名、部门、岗位和机构。

用户改名、调岗或部门移动后，历史考试名单、部门统计和导出内容会随当前账号资料变化。

建议考试发布时保存人员档案快照，至少包含：

- 用户 ID、账号、姓名。
- 当时所属机构、部门及部门路径。
- 工号、岗位和职务。
- 分配来源和解析时间。

快照用于历史展示与统计分组，当前用户表只用于账号有效性和最新信息查询。

### P1-04 综合成绩缺少不可变正式计算版本（已修复）

当前综合成绩计算来源保存在可修改的 `sts_evaluation_record_item.calculation_source_json`，评价记录和参训人员汇总字段也可更新。设计没有定义：

- 哪一条计算记录是当前正式结果。
- 同一参训人员和表单版本是否允许多个 `CALCULATED` 记录。
- 重算时覆盖旧记录还是产生新版本。
- 已确认但尚未归档的历史成绩如何锁定。

建议增加只追加的计算批次，或至少补充：

```text
calculation_run_id
calculated_time
confirmed_time
official_status
supersedes_record_id
calculation_hash
```

每次计算保存使用的规则版本、课程报名、考试人员、线下成绩、奖惩记录、来源分、权重、中间结果和最终结果；新计算不得覆盖已确认结果。

### P1-05 监管预警缺少去重与触发幂等（已修复）

`sts_regulation_warning` 只有查询索引，没有稳定幂等键。定时检测重试、并发调度或规则重复执行时，可能为同一规则、机构和培训计划生成多条相同
OPEN 预警。

建议增加 `dedup_key` 或 `detection_cycle`，按已确认口径建立唯一约束，例如：

```text
warning_rule_id + regulated_org_id + training_plan_id + detection_cycle
```

如果业务允许同一周期重复告警，应增加明确的 `occurrence_no` 和关闭后再触发规则，不能依赖应用查询后再插入。

## 6. 一致性与实施准备问题（P2）

### P2-01 `design.md` 与 DDL 的课程设置模型仍不一致

`design.md` 描述 `sts_course_setting` 包含 `setting_name`、`is_default`，并允许机构内多个命名设置；DDL 实际没有这两个字段，并通过
`organization_id + deleted` 约束为每机构一条配置。

此外，`design.md` 使用 `is_self_enrollment_allowed`，DDL 使用 `is_self_enroll_allowed`。字段级设计来源不唯一会直接影响后续
API、Entity 和 migration。

需要确认课程设置是：

- 每机构一条统一设置；还是
- 每机构多套命名设置，由课程选择或指定默认项。

确认后同步 `design.md`、DDL 和 `table-catalog.md`。

**处理记录（2026-07-21，见 `design-review-issues-round2.md` R2-12）**：按"以已确认 DDL 为准"的原则，`design.md`
已改为每机构一条统一设置并统一 `is_self_enroll_allowed` 命名，与 DDL、`table-catalog.md` 三方一致。若产品后续要求机构内多套命名设置，需另行发起设计变更。

### P2-02 当前 DDL 不是可执行 migration，系统表扩展需要分阶段回填

`00_system_permission_extension.sql` 直接向已有 `us_sys_dept`、`us_sys_role` 增加非空 `organization_id`
、编码和角色级别字段。正式环境已有部门、角色数据时，不能直接应用该目标结构。

正式 migration 至少需要：

1. 创建机构表及必要平台/现有机构记录。
2. 以可空方式增加系统表字段。
3. 根据现有数据制定部门、角色的机构归属和业务编码回填规则。
4. 检查重复编码和无归属记录。
5. 将字段改为非空并创建唯一键。
6. 更新 Entity、API Contract、权限缓存和自动化测试。

## 7. 尚未确认的业务规则

以下规则在 `design.md` 中仍标记为待确认，表结构只能提供候选承载方式，不能据此认定需求已经满足：

1. 平台公共资源、跨机构授权级别及监管人员进入机构管理中心后的权限范围。
2. 课程无限级目录、单/多章节切换和发布后调整边界。
3. 文档、图文、音视频的有效学习时长、离屏计时、课程过期和完成重算口径。
4. 在线考试、线下考试、专项训练和题库练习的最终类型与限制。
5. 试卷与考试的时长、及格线、题序和多选评分优先级。
6. 补考次数、补考范围、最终成绩取最高或最后、改分与发布后可见性。
7. 外部人员临时注册、账号归属、数据保留与隐私授权。
8. 培训和阶段状态机、扫码加入、签到有效性及线下成绩导入冲突处理。
9. 证书变量、编号、签章、防伪、有效期、补发、撤销和纸质领取规则。
10. 考试、课程、培训、园区统计的计算口径及归档时点。
11. 预警规则来源、等级、通知、处置 SLA、关闭/忽略权限和导出口径。
12. 数据库时区、数据保留、冷归档、脱敏和大表分区阈值。

这些规则在对应业务 Task 实施前必须确认。需要改变表结构、API Contract、权限或数据库边界的确认结果，应先更新本 OpenSpec
Change，再进入 codeHarness。
