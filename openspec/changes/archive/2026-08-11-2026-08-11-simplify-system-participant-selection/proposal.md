# Proposal：全系统简化参与人员选择

## Why

系统当前通过 `sts_common_audience`、`sts_common_audience_rule`、`sts_common_audience_member` 保存通用参与范围，支持动态/冻结、
包含/排除、标签、岗位和嵌套范围。课程、考试、培训、问卷和直播分别保存 `audience_id`，部分业务再从冻结成员生成报名、考生或参训人。

系统尚未上线且没有业务历史数据。当前业务只需要“按本机构全员、部门或人员筛选，然后确认到具体人员”，继续保留通用规则引擎会增加配置、
接口、权限和数据追溯成本。因此统一改为：筛选条件只参与当次解析，最终业务事实只绑定具体用户。

## What Changes

1. 新增无持久化规则的统一人员选择解析能力，只接受当前机构全员、部门和指定人员，解析结果为去重后的启用用户 ID。
2. 课程指派报名、考试分配、培训参训和问卷投放均把解析结果直接写入各自人员事实表。
3. 课程开放报名使用开课级具体人员白名单；全员开放不写白名单，部门/人员选择在保存时展开为具体用户。
4. 课程直播不再单独配置参与范围，访问资格继承课程开课报名。
5. 问卷提交必须基于已绑定参与人；结果查看由既有功能权限控制，不再配置结果可见范围。
6. 删除公共参与范围 API、菜单、权限、后端领域实现和三张数据库表。
7. 删除课程、考试、培训、问卷、直播中的 `audience_id` 及通知范围字段，调整相关 OpenAPI。
8. 不提供历史兼容、双写或数据迁移；开发和测试数据直接按新模型重置。

## 用户价值

- 部门只是选人工具，最终名单清楚、稳定、可审计。
- 不再要求用户理解范围模板、冻结、排除、嵌套等抽象概念。
- 课程、考试、培训和问卷采用同一种选人语义。
- 删除未上线的复杂基础设施，减少权限入口、接口和数据表。

## 范围

- 课程开课、报名、开放报名资格和直播访问。
- 考试人员分配及结果通知范围字段。
- 培训计划参训人员绑定。
- 问卷投放参与人及结果查看范围。
- 公共参与范围后端、Contract、菜单权限、schema 和 migration。
- 统一人员选择解析服务及其 OpenAPI Contract。

## 非目标

- 不实现标签、岗位、排除、嵌套、动态跟随或冻结范围。
- 不实现链接令牌、邀请码、匿名外链或外部人员参与。
- 不实施前端页面、Mock 或 UI；前端以 OpenAPI 为准另开。
- 不修改人员、部门、角色数据范围和机构隔离模型。
- 不修改业务完成、判分、综合成绩或评价算法。

## 风险

- 同时修改五个业务域的 API Contract 和数据库字段，必须按已确认 Task 分批完成并执行真库回归。
- 部门选择在确认时展开为用户快照，后续调岗不会自动增删已绑定人员；调整名单必须显式重新选择。
- 开放报名白名单可能较大，需要唯一索引、批量写入和分页查询，禁止把用户 ID 数组塞入 JSON 字段。
