# 培训域设计现状与开发就绪性评审

> 评审日期：2026-08-26
>
> 文档状态：现状评审与长期架构输入；未确定结论均标记为“暂定”。
>
> 本文不是 OpenSpec，不新增实施授权、业务 Task、API Contract、权限语义或数据库变更。后续实施范围、业务规则、验收标准和变更授权仍以人工确认的
`openspec/changes/` 及 `docs/api/*.openapi.json` 为准。

## 1. 评审结论

课程、题库、试卷和考试已经具备培训域继续建设的主要后端前提，但培训域当前不适合直接沿用旧设计全面实施。

当前培训设计已经形成“类型、标准、模板、计划、执行、结果”的领域骨架，且后端存在较多基础实现；但课程与考试的稳定版本引用、培训考试来源、执行实例创建、计划状态机、完成与合格规则、多端真实执行等关键逻辑尚未闭合。特别是
2026-08-25 完成的课程考核与独立考试来源分离已经改变考试执行边界，现有培训考试接入方式与最新 `AssessmentExecution` 模型不一致。

因此，就绪性判断为：

| 范围              | 判断         | 说明                                       |
|-----------------|------------|------------------------------------------|
| 培训类型、标准、模板、评价表单 | 基础具备，可继续补齐 | 已有数据结构、后端 API 和部分管理页面，但真实联调及引用约束仍需闭合     |
| 培训计划输入与线下执行     | 基础具备，需先补规则 | 已有计划、阶段、参训人、线下场次、签到、成绩等实现，但状态机和业务生效规则不完整 |
| 培训课程与考试执行       | 暂不具备直接实施条件 | 必须先对齐课程稳定版本、`TRAINING_EXAM` 来源和统一考核执行边界  |
| 培训完整端到端交付       | 未就绪        | 管理端计划工作台、教师执行页、学员 PC/移动培训任务及真实接口验收尚未闭合   |

## 2. 培训域与课程、考试的关系

培训不是课程或考试的替代品，而是组织课程、题库、考试和线下活动的一次业务执行容器。

```text
培训类型
  → 培训标准
  → 培训模板
  → 培训计划
      ├── 课程：形成学习进度、学习时长和课程结果
      ├── 题库：形成练习次数、正确率和错题事实
      ├── 考试：形成作答、判分、批阅和正式成绩
      ├── 线下培训：形成签到、线下学时和线下成绩
      ├── 评价、奖惩和附件
      └── 参训人员分项结果与最终培训结果
```

课程和考试是可复用资源及执行能力；培训计划负责为特定人员、时间和业务目的组织这些能力，并将结果归集到明确的
`trainingParticipantId + planContentId` 上下文。相同课程、试卷或题库被不同培训复用时，执行事实和结果不得串联。

## 3. 现有设计中合理且应保留的部分

### 3.1 领域分层

现有“培训类型 → 培训标准 → 培训模板 → 培训计划”的分层应保留。各层产物与禁止越界带入以
`docs/architecture/training-layer-responsibility.md` 为准（本文 2026-08-26 评审不替代该职责定义）：

- 培训类型表达工种和培训业务分类，并承载初培学时、复审学时、线上最高占比等基础指标（尺子，不排课）。
- 培训标准表达带版本、有效期和发布状态的检查口径，可加严总学时、线上占比，并可声明必含课程、考试和线下；不是可编辑课表。
- 培训模板表达可复用的阶段及内容编排，不等于一次实际培训，不配本期人员与执行参数。
- 培训计划表达一次实际业务任务，包含时间、地点、负责人、参训人、阶段、内容和来源快照；发布后调用开课/考试能力。

### 3.2 历史稳定性与机构边界

现有设计已经具备以下正确方向：

- 类型、标准、模板和计划按当前机构严格隔离。
- 标准、模板和评价表单采用发布版本或不可变版本语义。
- 计划发布后冻结类型、标准、模板来源快照及哈希。
- 已发布计划结构应保持只读，来源资源后续变化不应改写历史执行事实。
- 参训人按 `(trainingPlanId, userId)` 保持唯一。
- `TrainingExecutionLink` 用于连接计划内容和真实执行实例，不允许使用资源 ID 冒充执行实例 ID。

### 3.3 执行事实边界

现有后端已经覆盖或建立了以下基础边界：

- 课程开课和课程报名事实。
- 考试 Candidate、Attempt、作答、批阅和成绩事实。
- 培训线下场次、签到、成绩、附件和奖惩事实。
- 学员本人培训任务和参训详情读取入口。
- 课程、考试和线下分项结果读取及同步入口。
- 评价表单固定版本与培训计划的绑定。

这些资产可以复用，但需要按后续确认的培训执行语义重新连接。

## 4. 当前设计和实现的主要缺口

### 4.1 培训考试仍依赖旧的独立考试模型

最新考试架构已经把题库/试卷资源、课程内容、独立考试任务和统一考核执行事实分层，并以 `AssessmentExecution.sourceType`
表达结果归属。现有培训代码仍通过 `examId` 查找独立考试，调用 `requireStandaloneByExamId()`，再以独立考试入口创建培训学员作答。

这会造成以下问题：

- 培训考试继续借用独立考试任务，业务来源不再是一等事实。
- 同一试卷在独立考试、课程和培训中复用时，存在结果归属混淆风险。
- 培训考试无法完整继承最新按执行对象隔离的 Candidate、Attempt、Reviewer 和成绩链。
- 最新设计已明确将 `TRAINING_EXAM` 保留给后续独立 OpenSpec，现有培训实现不能视为已对齐。

暂定架构方向：培训考试内容直接冻结已发布试卷版本，题库练习直接冻结题库引用；计划发布或执行准备时生成
`sourceType=TRAINING_EXAM`、以计划内容为稳定来源的 `AssessmentExecution`。该方向必须在新的 OpenSpec 中人工确认。

### 4.2 计划内容没有完整冻结课程、试卷和题库版本

当前培训模板及计划内容主要使用 `contentType + resourceId` 表达引用，而计划发布主要冻结培训类型、标准和模板。现状不足以稳定表达：

- 课程实际执行的 `courseVersionId`。
- 培训考试使用的 `paperVersionId`。
- 题库练习使用的 `questionBankId` 及开考时题目冻结规则。
- 发布时的资源名称、状态和必要显示快照。
- 每项内容的执行规则及校验哈希。

如果不补齐，计划发布后无法严格重放“当时要求学员学习或考试的具体版本”。

### 4.3 内容保存和发布缺少完整资源校验

当前计划阶段替换主要校验内容类型枚举；计划发布主要复核培训类型、标准和模板。尚未完整闭合以下约束：

- 引用资源必须属于当前机构。
- 课程、题库和试卷必须已发布、启用且可执行。
- 内容类型必须与资源类型一致。
- 课程和试卷必须冻结稳定版本。
- 草稿保存后、正式发布前必须在同一事务内重新复核资源状态。
- 拒绝跨机构资源时不得泄露对方资源名称或所属机构。

统一候选资源查询只能辅助前端选择，不能替代写入和发布时的服务端校验。

### 4.4 执行实例“生成”尚未形成真实编排

当前实现可以为线下内容创建场次，但课程和考试分支主要查找预先存在、已带 `planContentId` 的 `CourseOffering` 或 `Exam`
，找到后再建立 execution link；找不到则报错。

因此当前能力更接近“连接既有执行实例”，尚未完整实现：

```text
计划内容
→ 校验并冻结资源
→ 创建或复用课程开课/培训考试执行对象
→ 为每名参训人创建或复用课程报名/Candidate
→ 建立 execution link
→ 返回可供学员进入的真实执行实例
```

原设计提出的集中执行编排 Module/Adapter 方向合理，但实际职责尚未闭合，培训 Controller 和 Service 仍直接依赖课程、考试
Mapper。

### 4.5 题库内容可保存但不能形成完整执行

培训内容枚举包含 `QUESTION_BANK`，统一引用查询也能返回题库，但当前执行解析仅能处理课程和考试，题库分支会进入“不支持的执行类型”错误。

这意味着“理论题库练习”目前只有引用和数据结构，没有学员开始练习、冻结题目、保存答题、统计正确率和错题、回写培训结果的真实闭环。

### 4.6 培训计划状态机不完整

数据模型定义了 `DRAFT/PUBLISHED/RUNNING/ENDED/CANCELLED/ARCHIVED`，但当前公开业务操作以创建、编辑和发布为主，尚未形成完整的：

```text
DRAFT → PUBLISHED → RUNNING → ENDED → ARCHIVED
                         ↘ CANCELLED
```

需要明确并实现的长期语义包括：

- 开始、结束、取消和归档由谁执行。
- 每次状态转换的时间、权限和前置条件。
- 到期是否自动结束，还是只允许人工结束。
- 结束前是否必须完成全部必修内容和线下事实确认。
- 取消后课程、考试和线下执行实例如何处理。
- 培训结果、档案、证书和监管统计分别从哪个状态开始生效。

### 4.7 完成、合格和综合成绩规则未闭合

计划内容已经设计 `isRequired`、`isScored`、`scoreWeight`、`scoreAggregationMode` 和 `requiredHours`
，但当前培训分项同步主要按课程、考试和线下类型求平均，尚未完整应用这些配置。

以下规则仍需人工确认：

- 必修内容未完成时能否结束培训。
- 考试不合格是否允许培训完成，完成与合格是否分离。
- 补考取最高分、最后一次成绩还是最后一次正式发布成绩。
- 多个课程、考试和线下成绩如何加权及聚合。
- 线上和线下有效学时如何确认。
- 奖惩、人工调整及异常值何时进入综合成绩。
- `PASSED/FAILED/INCOMPLETE` 的正式判定条件。
- 正式综合成绩是同步计算、人工确认，还是在培训结束后生成不可变计算批次。

在这些规则确认前，现有结果同步只能作为分项事实汇总，不能直接代表正式培训结果。

### 4.8 计划没有明确区分初培和复审

培训类型同时保存初培学时和复审学时，但培训计划没有明确记录本次培训属于初培还是复审。系统因而无法可靠判断应该选择哪一组基础学时要求，也无法稳定支撑标准校验、统计和监管预警。

设计结论：在计划中把培训类型与培训性质分离，培训性质使用 `INITIAL`（初培）/`REVIEW`（复审）；发布时冻结性质和适用最低学时。历史计划不
猜测，使用只读兼容值 `UNSPECIFIED`。具体字段、迁移、契约和监管预警兼容方案已进入待人工确认的 OpenSpec Change
`2026-09-01-add-training-plan-nature`，确认前不得实施。

### 4.9 模板引用尚未形成明确的实例化规则

计划可以记录 `sourceTemplateId`，但模板阶段和内容如何进入计划草稿仍需明确。长期语义至少应回答：

- 选择模板时是否立即复制阶段和内容。
- 复制后的计划允许修改哪些字段。
- 模板发布新版本是否影响已经创建的草稿计划。
- 计划发布时冻结源模板，还是冻结计划修改后的最终编排。

暂定方向：引用模板时复制为独立计划草稿；之后计划可在授权范围内编辑；发布冻结计划的最终编排及其来源信息，模板后续变化不回写计划。

### 4.10 管理端和学员端没有形成真实闭环

当前管理端已有培训类型、标准、模板和评价表单页面，但相应 API 默认仍可能走 Contract Mock。尚未看到完整可验收的：

- 培训计划列表和独立计划工作台。
- 阶段、内容、评价表单和参训人员编排。
- 执行实例准备及状态管理。
- 教师线下任务、签到确认和成绩录入页面。
- 管理员参训结果与异常处置页面。
- 学员 PC 和移动端培训任务、内容进入和结果页面。

PC 学员培训中心当前仍是“培训中心暂未开放”的占位页面。Mock 页面、菜单和路由不能作为培训业务已完成的依据。

`engineering/plans/end-to-end-development-progress-tracker.md` 将 M3 培训执行闭环标记为“已完成”，但当前未归档的培训
OpenSpec 仍记录：

- `2026-07-29-complete-m3-training-execution-loop` Task 1、Task 2 为阻塞，Task 3～6 未开始。
- `2026-08-04-complete-m3-reference-resource-contract` Task 1 未获得完整 MySQL IT 通过证据，Task 2、Task 3 待确认。
- 培训计划管理端、教师端和学员端未形成真实接口端到端闭环。
- 最新考试来源模型尚未回接培训考试执行。

按照项目“OpenSpec Task、真实纵向闭环和验收证据优先”的完成口径，当前 M3 不应被解释为产品端到端已完成。更准确的长期状态描述是：

> 培训后端定义和基础执行能力已部分落地；课程/考试执行集成需要重新对齐；管理端、教师端和学员端真实闭环尚未完成。

本文不直接修改进度表；状态修正应在后续已确认 OpenSpec Task 完成、Review 和验收后按项目规则更新。

## 6. 后续设计必须先确认的业务决策

以下内容是后续 OpenSpec 的确认输入，不是本文直接确定的业务规则：

| 决策       | 当前暂定建议                                                            | 影响                    |
|----------|-------------------------------------------------------------------|-----------------------|
| 培训考试引用对象 | 直接引用已发布试卷版本，生成 `TRAINING_EXAM` 执行对象                               | 考试来源、数据模型、API、批阅和结果归属 |
| 培训题库引用对象 | 直接引用题库，开考时冻结可用题目版本                                                | 题库练习、正确率、错题和完成规则      |
| 培训课程引用对象 | 冻结课程版本，并为计划内容创建独立 CourseOffering                                  | 开课、报名、学习事实和结果回写       |
| 初培/复审    | 已形成待确认 Change：计划保存 `INITIAL/REVIEW`，发布冻结适用最低学时；历史值为 `UNSPECIFIED` | 学时标准、统计和监管预警          |

| 计划状态转换   | 明确人工/自动触发、前置条件和副作用                                                | 执行实例、结果、档案和统计         |
| 模板实例化    | 复制为计划草稿，发布冻结最终计划编排                                                | 模板版本、计划编辑和历史追溯        |

## 7. 建议的演进顺序

以下仅说明架构依赖顺序，不构成实施 Task 或开发授权：

1. 培训内容引用、执行和结果闭环已由既有 OpenSpec 落地；初培 / 复审及对应学时判定由待确认 Change
   `2026-09-01-add-training-plan-nature` 独立补齐，确认前不实施。
2. 对齐课程版本、试卷版本、题库引用和培训计划内容快照，使计划发布能够稳定重放。
3. 建立统一培训执行编排边界，幂等创建课程开课、培训考核执行、课程报名、Candidate 和线下场次。
4. 补齐计划状态机、参训人员状态和课程/考试/线下分项结果回写。
5. 在稳定分项事实之上形成正式综合成绩、培训结果、档案和证书入口。
6. 完成管理端、教师端、学员 PC/移动端真实接口联调，并以真实纵向链路完成验收。

完整验收链路应最终能够证明：

```text
管理员维护类型、标准和模板
→ 创建并发布培训计划
→ 冻结课程、试卷/题库及规则版本
→ 圈定参训人员并幂等生成真实执行实例
→ 学员完成课程、培训考试/练习和线下培训
→ 教师完成签到确认、线下成绩和必要批阅
→ 系统归集可追溯分项事实
→ 按确认规则形成正式培训结果
→ 管理员和学员查看同一份结果事实
```
