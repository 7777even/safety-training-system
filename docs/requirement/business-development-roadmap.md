# 业务开发路线图

## 开发原则

以业务闭环和已确认依赖排序，而非按前端页面或后端接口拆分。每个阶段遵循“OpenSpec → 确认 → API Contract First → 前后端实现 → 测试与 Review → QA / Retro”；一次最多连续实施 3 个已确认 Task。

## 每个阶段的固定关卡

1. **规格关卡：** 在 `openspec/changes/` 创建 `proposal.md`、`design.md`、`tasks.md`、`spec-delta.md`，列出 FR 覆盖和未确认项。
2. **确认关卡：** 产品、架构和权限责任人确认业务规则、数据范围、外部服务与原型边界；未确认项不得进入编码任务。
3. **契约关卡：** 先在 `docs/api/` 定义 URL、方法、参数、返回、错误码、权限和示例；若涉及持久化，先确认 migration。
4. **实现关卡：** 按 `tasks.md` 一次执行一个业务 Task；前后端只实现当前 Task 覆盖的 FR。
5. **质量关卡：** 完成契约测试、权限与数据范围测试、关键业务流程测试和回归；记录 QA、Review 与 Retro。

## 不得跳过的依赖决策

- 文件存储、转码服务、预览能力与大文件限制；这些决定课程资源的技术边界和成本。
- 课程分类、章节目录、学习时长、完成条件、合格条件及重学规则。
- 课程开课可见范围如何复用既有组织数据范围；业务资源严格限制为所属机构，不提供跨机构授权。
- 消息、直播、微信、扫码、人脸识别和仿真软件的接入方式；均为外部或跨端能力，不能以模拟实现替代最终规则。
- 统计指标、证书签发和监管预警的计算口径；必须在产生数据前确认，否则历史数据无法可靠回算。
