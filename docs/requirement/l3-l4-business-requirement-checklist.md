## 1. 口径

### 1.1 级别判定

级别取自 `AGENTS.md` 第 2 节的变更风险分级：

| 级别 | 适用范围 | 最低流程 |
|---|---|---|
| L3 | 课程、考试、培训、成绩、档案、证书、统计、预警及相关业务页面/API | OpenSpec → 人工确认 → TDD 实现 → 定向测试 → Review → QA/Retro |
| L4 | API 契约、权限模型、数据库、架构、生产部署或跨端协议 | 按 L3，并在实施前取得人工确认；数据库同步 migration |

本清单的判定规则（逐条应用，取最高级别）：

1. 需求落在课程 / 考试 / 培训 / 成绩 / 档案 / 证书 / 统计 / 预警业务域 → **L3**。
2. 需求引入或修改 **API 契约、权限码、数据库结构或迁移、架构组件、跨端（PC↔移动↔第三方）协议** → 升为 **L4**。
3. 已明确延期或退役的需求 → 不入清单（见 §6.3）。
4. 纯样式、文案、局部交互 → 属 L1/L2，不入清单（例：2026-09-29 的侧栏滚动、表格列宽、成绩可见性文案修正）。

### 1.2 数据来源与统计口径

- 功能项：`docs/product/功能项.csv` 第 1～87 项。**1～50 为中山园区、51～87 为裕龙园区**。
- Change 覆盖：脚本扫描 `openspec/changes/**`（活动 **0** 个 + 归档 **171** 个目录）下全部 `.md`，
  提取「功能项 N」显式引用；命中位置主要是 `proposal.md` 的「功能项追溯 / 覆盖功能项」小节与 `tasks.md` 的「输入：功能项 N」。
- 引用写法支持枚举（`功能项 1、3、7`）。**2026-09-30 修正**：旧版正则只取枚举首项，曾把 7、24、41 误记为「无引用」，
  并因此在旧版 §2 得出「活动 Change 引用功能项 = 0、有引用 41」的偏低结论；本版已按修正后的扫描重算。
- Change 名一律写**归档目录真实名**，以 `ls openspec/changes/archive/` 的结果为准，不按规则推断。
  多数目录名等于 Change 名（如本次归档的 `2026-09-29-close-m5-pc-regulation`，归档未再加日期前缀），
  但有一批历史目录带重复日期前缀（如 `2026-09-20-2026-09-20-realign-m5-minimum-closure`）；早期 Change 名内不带日期
  （`align-training-layer-apis`、`unify-cover-access-protocol`、`exclude-exam-from-training-hours` 等）。
  旧版清单写的是被剥掉前缀的短名，`ls` 定位不到，本版已全部订正（56 个引用经脚本校验 0 处悬空）。
- 覆盖统计**只识别显式引用**。以「第 N 项」「相关语义」等措辞引用、或纯靠能力语义覆盖的需求不会被计入，
  因此「无 Change 引用」≠「完全没有实现」，只代表**没有可追溯的规格承诺**。
- 能力编号（`COURSE-xx` / `EXAM-xx` / `TRAIN-xx` 等）沿用
  `engineering/plans/end-to-end-development-progress-tracker.md` 第 3 节。

## 8. 维护规则

- 本清单是派生视图，不产生实施授权。新增需求仍须走 `openspec/changes/` 与人工确认。
- Change 归档、任务状态变化、功能项.csv 修订后，需同步刷新 §1.2/§2 汇总、§3/§4 状态与 §5 覆盖矩阵。
- §5 覆盖矩阵由脚本从 `openspec/changes/**` 扫描生成（正则 `功能项\s*(\d{1,3}(?:\s*[、,，和及]\s*\d{1,3})*)`），
  刷新时勿手工编辑该节，避免与扫描结果漂移。
- 状态列的更新必须能追溯到进度表、QA 或验收证据；无证据时写「未验证」，不写「应该已通过」。
- Change 名一律使用归档目录真实名（以 `ls openspec/changes/archive/` 为准，不推断命名规则），便于直接定位。
